# 블로그 초안

세션에서 실제로 일어난 일을 근거로, 블로그에 그대로 옮길 수 있는 글 한 편을 `blog-drafts/`에 쓴다.

## 입력

- 인자로 주제·강조점·독자 수준이 오면 따른다. 없으면 세션에서 가장 의미 있는 문제 하나를 고른다.
- 주제가 여럿이면 한 흐름으로 묶일 때만 합친다. 묶이지 않으면 후보를 짧게 보여 주고 고르게 한다.

## 순서

1. **기존 초안을 읽는다.** `blog-drafts/`의 최근 글 한두 편으로 제목·요약·절 구성·문장 길이를 맞춘다. 같은 연재(부하 테스트 등)면 앞 글과 이어지게 쓴다.
2. **사실을 모은다.** 목표와 배경, 증상(오류 메시지·로그·측정값), 원인 분석(가설 → 근거 → 결론, 틀렸던 가설), 해결(핵심 diff·설정, 고른 이유, 버린 대안), 검증(실행한 명령과 결과, 실행하지 않은 범위).
   추측으로 채우지 않는다. 부하 측정 글이면 `../gatling-test/docs/capacity-log/`의 그날 일지를 함께 원본으로 쓴다.
3. **코드는 원본에서 인용한다.** 대화에 일부만 있으면 파일이나 커밋(`git show`)을 읽어 정확히 옮긴다.
4. **그림을 만든다.** 번호 절마다 판단의 근거(전/후 차이, 병목이 드러나는 구간, 구조)를 보여 줄 그림을 정하고 [그림](#그림) 절대로 PNG를 만든다.
   원본이 없거나 캡처할 수 없는 그림만 자리 표시로 남긴다.
5. **민감 정보를 지운다.** 운영 도메인·IP·인스턴스 ID, DB 이름·계정, 비밀값·토큰, 컨테이너 이미지 이름, 이메일은 지우거나 일반화한다. 그림 속 글자(리포트 제목, URL, 호스트 태그)도 본문과 같이 확인한다.
   공개 저장소(`ticket-project/ticket-core`, `ticket-project/gatling-test`)와 클래스 이름은 써도 된다. 무엇을 가렸는지 응답에 목록으로 알린다.
6. **쓰고 저장한다.** 아래 양식과 문체를 따른다. 저장한 경로, 만든 그림과 자리만 남긴 그림, 가린 정보, 사실 확인이 필요한 부분을 응답에 짧게 알린다.

## 양식

기존 초안(`blog-drafts/2026-10-12/ticket-loadtest-bottleneck-ladder.md`, `blog-drafts/2026-10-14/ticket-loadtest-part2.md`)과 같다. YAML 머리말은 쓰지 않는다.

```markdown
# <결과가 보이는 제목>: <주제를 밝히는 부제>

- <무엇이 문제였나, 핵심 수치는 굵게>
- <원인>
- <해결과 결과>

## 무엇을 쟀나 (또는 배경)

## 1. <단계별 소제목: 그 단계에서 알게 된 사실>
(증상 → 근거 → 판단. 전/후 표, 핵심 코드만)

배운 점: <한 줄>

## 2. ...

## 정리
(단계별 결과 표, 배운 점 목록, 다음에 할 일)
```

- 문제 해결이 아니라 기능·설계 기록이면 번호 절을 "요구사항 / 설계 선택지 / 구현"으로 바꾼다.
- 전/후 비교는 표로 쓴다. 수치는 세션이나 일지에서 측정한 값만 쓴다.
- 그림은 `![설명](<slug>-N.png)`로 같은 폴더에 둔다. 만들 수 없으면 `<!-- 그림 N: 캡처할 화면과 시간 범위 -->`로 자리를 남긴다.

## 그림

그림 한 장은 판단 하나를 보여 준다. 기존 초안의 그림처럼 제목은 그 그림이 보여 주는 결론 한 문장, 부제는 조건(초당 N명 × 초, DB 연결 수), 아래 한두 줄은 읽는 법(두 차트의 축 눈금이 다르면 그 사실)이다.

부하 측정의 원본은 그날 일지가 가리키는 실행 폴더 `../gatling-test/distributed-results-join/capacity/<YYYYMMDD-HHMMSS-용도-부하>/`다.

| 보여 줄 것 | 원본 | 만드는 법 |
| --- | --- | --- |
| 요청 응답 시간, 초당 요청·응답 | 실행 폴더의 Gatling 리포트 `<simulation>-<시각>/index.html`. 운영 원격 실행에는 없다(바이너리 `simulation.log`뿐) | 차트 요소를 캡처한다: `#ResponseTimeContainerId`(응답 시간 백분위), `#RequestsContainerId`·`#ResponsesContainerId`, `#ResponseTimeDistributionContainerId` |
| 서버 연결·스레드·CPU 추이 | 실행 폴더 `core-metrics.tsv`(시각별 `hikari_active`·`hikari_pending`·`tomcat_busy`·CPU, 조회 실패는 `TIMEOUT` 행) | HTML에 인라인 SVG로 그린다 |
| 사용자별 머문 시간·결과 | `booking-results.csv`(`startedAt`·`flowCompletedAt`·`coreResidenceMillis`·`result`), `summary.json` | 인라인 SVG |
| 단계별 결과, 전/후 수치 | 일지 표, 세션의 측정값 | CSS 막대 |
| 구조(락·연결 풀이 물린 고리 등) | 코드와 본문 | SVG 도식 |
| Datadog trace·대시보드 | Datadog | 로그인된 브라우저 도구가 있을 때만 캡처하고, 없으면 자리 표시 |

1. 그림 HTML을 세션 임시 폴더에 쓴다. `body{width:720px;margin:0}`, 흰 배경, 글꼴 `"Malgun Gothic"`이다. 값은 원본 파일에서 읽은 그대로 넣는다.
2. `node .agents/skills/blog/capture.mjs <그림.html|리포트 index.html> blog-drafts/<날짜>/<slug>-N.png [CSS 선택자=body] [배율=2]`로 캡처한다.
   전/후 비교는 차트를 먼저 임시 폴더에 각각 캡처하고, 제목과 함께 `<img>`로 한 HTML에 모아 다시 캡처한다.
3. PNG를 열어 본다. 빈 차트가 아니고, 시간축이 행 순서가 아니라 실제 시각 간격이고, 축 범위가 최댓값을 자르지 않고, 글자가 잘리거나 겹치지 않고, 수치가 본문·표와 같을 때까지 고쳐 다시 찍는다.

## 문체

- 한국어 평서체(`~한다`, `~했다`)로 쓴다. 완결된 문장으로 끝맺고 조사·어미를 생략하지 않는다.
- 독자는 같은 기술 스택의 다른 개발자다. 세션 맥락("아까", "위에서")을 쓰지 않고 글만 읽어도 이해되게 쓴다.
- 작성자 1인칭이 기본이다. AI와 작업했다는 사실은 사용자가 원할 때만 넣는다.
- 부하는 "초당 N명"처럼 풀어 쓰고, 처음 나오는 용어는 한 번 풀어 준다.
- 코드 블록에 언어 태그를 붙이고 필요한 부분만 잘라 `// ...`로 생략을 표시한다.
- 과장 표현과 근거 없는 수치를 쓰지 않는다. 확인하지 못한 것은 "확인하지 못했다"고 쓴다. 엠대시(—)는 쓰지 않는다.

## 저장

- `blog-drafts/<YYYY-MM-DD>/<slug>.md`. 날짜는 다룬 작업의 날짜, slug는 `ticket-`으로 시작하는 영문 kebab-case다. 그림도 같은 폴더에 둔다.
- 커밋은 `docs(blog): <한국어 설명>`이다([CONTRIBUTING.md](../../../CONTRIBUTING.md)).

## 하지 않는 일

- 블로그 플랫폼에 게시하거나 외부로 보내지 않는다. 사용자가 명시적으로 요청하고 확인한 경우만 예외다.
- 세션에서 일어나지 않은 시행착오·결과를 꾸며 넣지 않는다.
