# Core 수용량과 Queue 입장률

Queue가 Core를 지키려면 숫자 하나가 필요하다. **Core에 1초에 들여보낼 새 예매 사용자 수**다. 이 문서는 그 숫자를
어떤 순서로 재고, 무엇을 보고 PASS/FAIL을 가르고, Queue 설정으로 어떻게 옮기는지 정한다.

숫자는 잰 조건에 묶인다. 코드, 서버 사양, 연결 풀, 테스트 데이터 가운데 하나가 바뀌면 다시 잰다. 그래서 잴 조건을
먼저 고정하고, 이상적인 사용자로 한계를 찾고, 실제 사용자에 가까운 흐름으로 확인한 뒤, 여유를 남긴 값을 Queue에
넣고, Queue를 켠 상태로 마지막 확인을 한다.

실행 방법(시나리오, feeder, 콘솔 입력)의 원본은 gatling-test
[운영 Core 안전 입장률 측정 가이드](https://github.com/ticket-project/gatling-test/blob/master/docs/core-capacity-production.md)다.
gatling-test 콘솔 맨 위의 **Core 수용량 측정** 패널이 아래 순서와 판정을 그대로 따른다.

## 왜 users/sec인가

Queue는 scheduler 주기마다 `advanceBatchSize`명씩 내보낸다(`ticket-queue` README의 Scheduler 절). Core가 느려져도
같은 속도로 계속 들여보낸다. 그래서 Core 쪽도 "초당 새 사용자"를 정해진 속도로 넣는 Open Model로 잰다. 최대 HTTP
RPS나 Closed Model의 동시 사용자 수는 Queue가 조절하는 값이 아니므로 입장률로 바로 쓰지 않는다.

한 사용자는 공연 요약 → 좌석 상태 → 좌석 선택 → 주문 생성 → 주문 조회 다섯 요청을 보낸다. 30 users/sec는 정상
구간에서 대략 150 requests/sec다.

## 출발점 (2026-10-01)

- Queue 기본값 `QUEUE_ADVANCE_BATCH_SIZE=500`, `QUEUE_ADVANCE_INTERVAL_MS=1000`(회차당 초당 500명)은 측정값이 아니다.
- 2026-08 운영 실측에서 10 users/sec는 전원 성공했고 20 users/sec에서 기술 실패가 31.7%였다. 그때 Core는 OSIV가 켜져
  있어 요청이 응답 끝까지 DB 연결을 쥐었다. 연결 풀·스레드는 전부 기본값이었다(Hikari 10).
- 그 뒤 OSIV를 껐으므로 8월 숫자는 지금 코드의 한계가 아니다. 새로 잰다.

## 측정 순서

각 단계는 독립 실행이다. 한 단계가 끝나면 리포트와 서버 지표를 보고 다음으로 간다. 측정 대상은 **운영 서버**다.
로컬 PC는 CPU·메모리·DB·네트워크가 달라서 운영의 한계를 대표하지 못한다. 운영에는 실사용자가 없는 시간에, 전용
부하 회차(`910000001~`, 대기열 정책 `FORCE_OFF`)로, 단계마다 대상·부하·시간을 확인하고 실행한다.

| # | 할 일 | 왜 | 끝난 기준 |
| --- | --- | --- | --- |
| 1 | 측정할 코드를 master에 넣고 배포한다. 측정이 끝날 때까지 좌석 선택·주문 경로를 바꾸지 않는다 | 옛 이미지로 잰 숫자는 버린다. 측정 중에 예매 경로를 바꾸면 처음부터 다시 잰다 | 운영에 뜬 commit이 측정할 commit과 같고 health가 UP이다 |
| 2 | Core보다 먼저 막힐 상한을 적는다. Hikari 풀, Tomcat 스레드, 서버 사양, Core nginx의 `worker_rlimit_nofile`·`limit_req`, DB 세션 상한 | 앞단이 먼저 막히면 Core가 아니라 그쪽을 잰다. 2026-08-04에는 nginx FD가 먼저 터졌고, 다른 실행은 `limit_req` 503으로 끝났다 | 값이 기록돼 있다. nginx와 DB 등급은 저장소에 없어 서버에서 직접 본다 |
| 3 | 부하 회차와 회원을 한 번에 넉넉히 만들고, 운영 규모를 가정한 배경 데이터(회원 100만·주문 500만)를 넣는다(`seedProd`의 부하 픽스처·회원·배경 주문 옵션, [seed](../seed/README.md)) | 실행마다 새 회차를 쓴다. 픽스처는 `910000001` 공연이 이미 있으면 통째로 건너뛰어 나중에 늘릴 수 없다. 판매 기간은 적재 후 30일이다. 빈 주문 테이블에서는 인덱스가 없는 조회도 빠르다(2026-10-01 로컬에서 주문 3.6천 건 → 1.4만 건에 p95 체류 80 → 1,103ms) | 쓸 회차마다 좌석 2,000석이 AVAILABLE이다. 회원 ID가 필요한 수만큼 있다. `MEMBERS` 100만, `ORDERS` 500만이고 통계를 다시 모았다 |
| 4 | 03 고정 조건을 1 users/sec × 5초로 한 번 돌린다 | 시나리오나 데이터가 틀리면 비즈니스 거절이 기술 실패로 섞여 용량이 낮게 나온다 | PASS, 비즈니스 거절 0명 |
| 5 | 03 고정 조건을 5 → 10 → 15 → 20 → 30 → 40 → 50 users/sec, 각 30초로 잰다. 첫 FAIL이 나오면 마지막 PASS와의 사이를 반씩 좁힌다 | Queue가 조절하는 값을 그대로 잰다. 30초면 한 사용자가 1초 안팎에 끝나 안정 상태에 충분히 들어간다 | 마지막 PASS와 첫 FAIL의 차이가 2 또는 마지막 PASS의 10% 이하다. 이때 마지막 PASS가 후보값 C다 |
| 6 | FAIL 단계에서 Hikari pending이 0보다 크고 CPU가 남으면 DB 세션 상한 안에서 풀을 조정하고 5를 다시 한다 | 한 번에 하나만 바꿔야 무엇이 숫자를 움직였는지 안다. 병목이 DB 연결이 아니면 풀을 키워도 소용없다 | 필요할 때만 한다 |
| 7 | 03-3 실제 사용자 흐름을 C users/sec × 15분으로 한 번 돌린다 | 30초로는 선점 만료(픽스처 600초), 주문 만료 작업(5분 주기), 선택 TTL(5분), Modulith 재처리 점검(1분)이 부하와 겹치지 않는다. 실제 오픈은 대기자가 빠질 때까지 수 분 동안 이어진다 | PASS. FAIL이면 C를 낮춰 다시 한다 |
| 8 | Queue 입장률 R을 계산한다(아래 "Queue 설정으로 옮기기") | 측정값에는 오차가 있고 실제 사용자는 시나리오와 다르게 움직인다 | R과 Queue 설정값이 정해졌다 |
| 9 | Queue를 켜고 확인한다. Core `ADMISSION_TOKEN_ENFORCEMENT_ENABLED=true`, admission secret을 Core·Queue에 같은 운영 값으로, Queue batch를 R로 바꾼 뒤 06 Queue의 Core 보호(유입 3R)와 05 순간 부하(R → 2R)를 돌린다 | 실제로는 Queue가 Core를 지켜야 한다. 유입이 R보다 훨씬 커도 Core가 버티는지, 잠깐 넘쳤을 때 회복하는지 본다 | 06 PASS, 05 이후 응답 시간과 성공률이 원래대로 돌아온다 |
| 10 | 숫자와 조건(commit, 풀, 서버 사양, 회차 좌석 수, 회원·주문 수, 날짜)을 남긴다 | 다음에 다시 재야 하는지 판단하는 근거가 된다 | Queue README의 "남은 운영 검증" 자리와 측정 기록(Issue/PR)에 있다 |

03-3은 남은 좌석 중에서 골라 재시도하고, 매진되면 `BUSINESS_REJECTED_NO_AVAILABLE_SEAT`로 비즈니스 거절에 센다.
그래서 2,000석 회차 하나로 "몇 분 만에 매진 → 이후 거절 → 선점이 풀려 다시 경합"을 재현한다. 03은 사용자마다 고유
좌석이 있어야 해서 15분을 돌리면 좌석이 수만 개 필요하므로 장시간 실행에 쓰지 않는다. 03-3도 회원은 사용자마다
고유해야 하므로 C × 900명이 필요하다.

API별 단독 측정은 순서에 넣지 않는다. 5단계 한계가 예상보다 낮을 때 어느 API가 먼저 막히는지 찾는 진단용이다.

## 판정 기준

한 실행은 아래 중 하나라도 해당하면 FAIL이다.

- Gatling이 실패로 끝났다(기술 실패율 assertion 등).
- 기술 실패 사용자 비율이 기준 이상이다. 기본 1.0%다.
- 과부하(E6003, 선점 락 대기 초과) 사용자가 1명이라도 있다.
- 03 고정 조건에서 사용자 한 명이 다섯 요청을 끝내는 시간(Core 체류 시간)의 p99가 상한을 넘는다. 기본 5,000ms다.
  예전 API별 p99 기준(요약·좌석 상태 700ms, 선택·조회 1,000ms, 주문 1,500ms)을 더한 4,900ms를 올린 값이다.

FAIL은 아니지만 03 고정 조건에서 비즈니스 거절이 있으면 "데이터 확인"이다. 회차를 다시 썼거나 좌석·회원 준비가
덜 된 것이므로 용량 결과로 쓰지 않는다. 중지한 실행과 증거 파일이 없는 실행도 쓰지 않는다. 같은 부하에서 FAIL이
한 번이라도 나오면 그 부하는 FAIL로 본다.

Gatling assertion은 2026-08-18부터 기술 실패율만 본다. 느린 응답을 KO로 세지 않으려는 결정이다. 응답 시간은
위 체류 시간 기준으로 따로 판정한다. 409 응답 분류(비즈니스 거절·과부하·기술 실패)는 gatling-test `CoreRejections`가
원본이다.

FAIL 원인은 같은 시간대의 서버 지표로 확인한다. 볼 지표는 [운영](operations.md#core-용량-관측)의 Core 용량 관측 절을
따른다. Hikari pending, Tomcat busy 스레드, CPU, GC, 5xx를 같은 시간축에 놓는다.

## Queue 설정으로 옮기기

- **입장률 R = C × 안전계수.** 안전계수는 0.6~0.7이고 기본 0.7이다. 소수점은 버린다.
- `QUEUE_ADVANCE_INTERVAL_MS=1000`을 유지하고 `QUEUE_ADVANCE_BATCH_SIZE=R`로 둔다. 둘은 함께 유입량을 정하므로 하나만
  바꾸지 않는다.
- batch는 **회차마다** 적용된다. 지금은 인기 회차가 한 번에 하나만 열린다고 가정한다. 동시에 N개가 열릴 수 있으면
  R을 N으로 나누거나 Queue에 회차를 합친 전역 예산을 둔다.
- Queue에는 Core 안에 동시에 들어와 있는 인원 상한이 없다. 속도만 제한하면 Core가 느려질 때 체류 시간이 늘어 사람이
  쌓인다(2026-08-04에 동시 1,395명). 먼저 속도 제한만 쓰고, 9단계 순간 부하에서 회복하지 못할 때 상한을 검토한다.
  상한을 두려면 Core가 퇴장 신호를 보내야 해서 설계가 커진다.

## 다시 재야 할 때

- 좌석 상태·선택·주문 경로의 코드가 바뀌었다.
- 연결 풀, 스레드, 인스턴스 수, 서버 사양, DB 등급이 바뀌었다.
- 회원·주문 수가 가정(회원 100만·주문 500만)과 크게 다르거나, 주문 경로가 읽는 인덱스가 바뀌었다.
- 실제 공연의 좌석 수가 테스트 회차(2,000석)와 크게 다르다. 좌석 상태 응답 크기가 좌석 수에 비례한다.

## 아직 없는 것

- 대기열 필수(`FORCE_ON`) 회차가 seed에 없다. 9단계의 06은 Queue의 방출 속도는 확인하지만, Core의 admission token
  검증까지 거치려면 그런 회차가 필요하다.
- 05·06은 feeder CSV를 직접 준비한다. 콘솔이 자동으로 만드는 것은 03과 API별 선택·주문 시나리오뿐이다.
- Core 앞단 nginx 설정과 운영 `docker-compose.yml`은 저장소 밖에 있다.
- 운영 DB 등급과 세션 상한을 확인하지 않았다. Always Free라면 세션 30개가 풀을 키울 수 있는 상한이다.
