# 좌석 분산 락 다시 설계하기(검토)

상태: C안으로 정함(2026-10-28, [스케일 아웃 결정 목록](scale-out-decisions.md) D2-1). 아래 8장의 3·4는 남았다. 구현하면 ADR로 옮긴다.
사용자가 "락을 다 갈아엎어도 된다"는 전제로 필요성부터 다시 봤다(2026-10-26).
코드 위치는 운영에 배포된 master `43fe8873` 기준이다.

## 쉬운 말 요약

- 지금 좌석 하나마다 Redisson 분산 락을 걸고, 예매 흐름 네 곳(좌석 선택, 주문 선점, 주문 후처리, 선점 해제)에서 잡는다.
- 이 락이 막는 것은 두 가지다. **(1) 좌석 상태가 엉키는 것**(선택과 선점이 같은 좌석에 동시에 생기거나, 해제가 남의 선점을
  지우는 것), **(2) 좌석 알림 순서가 뒤집히는 것**(이미 남이 잡은 좌석에 "비었음"이 늦게 나가는 것).
- (1)은 락 없이 막을 수 있다. Redis는 Lua 스크립트 하나를 중간에 다른 명령을 끼우지 않고 끝까지 실행한다. "확인하고 바꾸기"를
  스크립트 하나로 하면 된다. 선택 저장과 선점 저장은 이미 이렇게 한다. 남은 틈은 세 곳뿐이다.
- (2)도 락 없이 막을 수 있다. 알림 발행(`PUBLISH`)을 상태를 바꾸는 그 스크립트 안에서 하면, Redis가 상태가 바뀐 순서 그대로
  내보낸다. 이것은 수평 확장 결정 D2-1(Redis pub/sub relay)과 같은 길이다.
- 그러면 분산 락이 필요 없다. 03 흐름에서 사용자 한 명당 Redis 왕복이 약 21번에서 4~5번으로 준다(추정). 운영 프로파일에서
  Redis 통신이 Core CPU의 12.5%였으므로 약 10%를 덜 쓸 것으로 본다(추정, 미확인). 락 대기 실패(`E6003`)도 사라진다.
- 락을 다 걷어도 원래 없던 방어선은 여전히 없다. Redis가 데이터를 잃으면 같은 좌석의 PENDING 주문이 겹칠 수 있다
  ([남은 작업](../todo.md)의 "좌석 단위 DB 방어선"). 락은 이것을 막은 적이 없다. 결제를 붙이기 전에 따로 정한다.

## 1. 개념: 분산 락과 Lua 스크립트

| | 분산 락(Redisson `RLock`) | Redis Lua 스크립트 |
| --- | --- | --- |
| 하는 일 | Redis에 "이 좌석은 지금 내가 만지는 중"이라고 적고, 다른 서버·스레드는 그 표시가 사라질 때까지 기다린다 | 명령 여러 개를 한 덩어리로 보내면 Redis가 다른 명령을 끼우지 않고 끝까지 실행한다 |
| 묶을 수 있는 것 | Java 코드 여러 줄. Redis 왕복 여러 번, WebSocket 발행, DB 조회까지 | Redis 안의 일만. 키 읽기·쓰기, 만료 시각, `PUBLISH` |
| 비용 | 잡기·풀기에 왕복 2번 이상(좌석 N개면 잡기 N번), 경합하면 기다린다(지금 0.5초·5초) | 왕복 1번, 기다림 없음. 스크립트가 길면 그동안 Redis 전체가 멈춘다 |
| 실패 모양 | 기다리다 시간이 지나면 `E6003`("좌석 선점 처리 중") | 조건이 안 맞으면 바로 결과 코드로 돌려준다 |

둘 다 "같은 좌석을 동시에 만지는 것"을 막는다. 락이 필요한 경우는 묶어야 할 일이 Redis 밖(DB, 외부 호출)에 있을 때다.
지금 좌석 락 안의 일은 모두 Redis 읽기·쓰기와 알림 발행이다. 그래서 스크립트로 옮길 수 있다.

## 2. 지금 락 지도

좌석 락 키는 `LOCK:hold:{회차}:{좌석}`(`RedissonLockKeyFormatter`)이다. 잡을 때 leaseTime이 없어 Redisson watchdog이 10초마다
연장 작업을 예약한다(운영 프로파일 `redisson-timer` 0.6%).

| # | 위치 | 언제 | 락 안에서 하는 일 | 막는 것 |
| --- | --- | --- | --- | --- |
| L1 | `SeatSelectionWriter.java:60` `select` | 좌석 선택(대기 0.5초) | 선점 있는지 `GET` → 선택 Lua → `SELECTED` 발행 | 선택과 선점이 같은 좌석에 함께 생김, 알림 순서 |
| L2 | `SeatSelectionWriter.java:75` `deselect` | 좌석 해제(대기 0.5초) | 해제 Lua → 선점 있는지 `GET` → `DESELECTED` 발행 | 알림 순서 |
| L3 | `SeatSelectionWriter.java:92` `notifyReleasedIfFree` | 선택 만료·일괄 해제 알림(대기 5초) | 선택·선점 있는지 `GET` 2번 → `DESELECTED` 발행 | 알림 순서 |
| L4 | `CreateOrderUseCase.java:148` | 주문 선점(대기 5초, 좌석 수만큼) | 본인 선택 확인(Lua) → 선점 Lua | 확인과 선점 사이에 선택이 바뀜 |
| L5 | `CreateOrderUseCase.java:168` | 주문 저장 실패 보상 | 선점 해제(`GET` → 비교 → `DEL`, 원자 아님) | 해제가 남의 새 선점을 지움 |
| L6 | `HeldSeatPublisher.java:39` | 주문 커밋 뒤 | 선점이 아직 이 주문 것인지 `GET` → 내 선택 지우기(Lua) → `HELD` 발행 | 이미 풀린 좌석에 `HELD`가 늦게 나감 |
| L7 | `HoldReleaser.java:37` | 취소·만료 커밋 뒤 | 선점 해제(원자 아님) → 비었는지 `GET` 2번 → `RELEASED` 발행 | 해제가 남의 새 선점을 지움, 알림 순서 |

이미 스크립트 하나로 원자적인 것:

- 선택 저장 `SELECT_IF_ABSENT_SCRIPT`(`RedissonSeatSelectionStore.java:31`): 같은 좌석을 두 회원이 동시에 선택하지 못하고, 회원별
  한도도 넘지 않는다. **선점이 있는지는 보지 않는다**(그래서 L1이 필요하다).
- 선점 저장 `SAVE_IF_ABSENT_SCRIPT`(`RedissonHoldStore.java:33`): 좌석 여러 개를 전부 잡거나 하나도 안 잡는다. 같은 회원의
  선점인지 알려 준다. **본인이 선택한 좌석인지는 보지 않는다**(그래서 L4가 필요하다).
- 선택 해제 `RELEASE_IF_OWNED_SCRIPT`(`RedissonSeatSelectionStore.java:56`): 내 선택일 때만 지운다.

원자적이지 않은 것: 선점 해제 `RedissonHoldStore.release`(`RedissonHoldStore.java:108`)는 좌석마다 `GET`으로 holdKey를 비교하고
`RSetCache.remove`, `DEL`을 따로 보낸다. 락이 없으면 비교와 삭제 사이에 남의 선점이 끼어들 수 있다.

DB가 막는 것: 회원·회차당 PENDING 주문 하나(`uk_orders_pending_member_performance`, booking V4). **같은 좌석이 두 PENDING
주문에 들어가는 것은 DB가 막지 않는다**(`order_seats`의 유일 제약은 `(order_id, performance_seat_id)`뿐). 지금은 Redis 선점이
유일한 기준이다.

## 3. 락마다: 무엇을 막고, 락 없이 막을 수 있나

### L1·L4: 선택과 선점이 엇갈리는 경쟁

락이 없으면 이런 일이 생긴다.

```text
1. A가 좌석 7을 골라 둔다(선택 키 = A, 5분)
2. A가 주문한다 → 본인 선택 확인 통과
3. 그 순간 A의 선택 5분이 끝나 선택 키가 사라진다
4. B가 좌석 7을 고른다 → 선택 Lua는 선점을 보지 않으므로 성공, SELECTED(B) 발행
5. A의 선점 Lua → 선점 키가 없으므로 성공
→ B는 자기가 고른 좌석을 A가 잡은 줄 모르고 주문하다 E6000을 받는다
```

지금은 4번이 L1 락에서 기다렸다가, 5번이 끝난 뒤 선점을 보고 `E6000`으로 끝난다.

**락 없이 막는 법**: 두 스크립트가 서로를 확인하게 한다.

- 선택 Lua에 "그 좌석에 선점 키가 없을 것"을 더한다. 선택 키와 선점 키는 같은 `{perf:N}` hash tag라 한 스크립트에 넣을 수 있다.
- 선점 Lua에 "모든 좌석의 선택 키가 이 회원일 것"을 더한다. 지금 Java에서 하는 본인 선택 확인(`SeatSelectionService.requireSelectedBy`)을
  스크립트 안으로 옮긴다. `E4006`과 `E4007`을 가르는 "최근에 만료된 선택" 읽기는 스크립트가 실패했을 때만 따로 한다(지금과 같다).

그러면 3·4·5가 어떤 순서로 오든 Redis 안에서 한 줄로 선다. 4가 5보다 먼저면 A의 선점이 실패하고(`E4007`), 5가 먼저면 B의 선택이
실패한다(`E6000`).

### L5·L7: 해제가 남의 선점을 지우는 경쟁

```text
1. A의 주문이 만료돼 해제가 시작된다 → GET 좌석 7 = A의 holdKey(일치)
2. 그 사이 좌석 7의 선점 키가 TTL로 사라지고, B가 선택 → 주문으로 좌석 7을 잡는다
3. A의 해제가 DEL 좌석 7 → B의 선점이 지워진다
→ 좌석 7이 빈 것으로 보여 C가 또 잡을 수 있다. 같은 좌석의 PENDING 주문이 둘이 된다
```

선점 키 TTL과 주문 만료 시각이 같아서, 만료 해제가 도는 때는 바로 키가 사라지고 남이 잡을 수 있는 때다. 지금은 L7 락이 2번을 막는다.

**락 없이 막는 법**: 해제를 스크립트 하나로 한다. 좌석마다 "값이 이 holdKey일 때만 지운다"를 Redis 안에서 한다(compare-and-delete).
인덱스 정리와 메타 키 삭제도 같은 스크립트에 넣는다.

### L2·L3·L6·L7: 알림 순서가 뒤집히는 경쟁

```text
1. A의 선택이 만료 → 만료 처리기가 "좌석 7 비었나?" 확인 → 비었다
2. B가 좌석 7을 고른다 → SELECTED(B) 발행
3. 만료 처리기가 DESELECTED 발행
→ 화면에는 좌석 7이 비어 보이지만 실제로는 B가 선택 중이다
```

지금은 1과 3을 같은 락 안에 묶어 2가 끼지 못한다. 주문 후처리(L6)와 해제(L7)도 같은 이유로 확인과 발행을 락 안에서 한다.

**락 없이 막는 법**은 둘이다.

- **스크립트 안에서 발행한다.** 확인과 `PUBLISH`를 한 스크립트에서 하면 2가 1과 3 사이에 끼지 못한다. Redis가 스크립트를 하나씩
  실행하고 `PUBLISH`를 처리한 순서대로 구독자에게 보내므로, 서버가 여러 대여도 알림 순서가 상태 변화 순서와 같다. 이 메시지를
  받아 각 서버의 WebSocket으로 나눠 주는 구독자는 D2-1의 relay가 그대로 맡는다.
- **좌석마다 버전 번호를 붙인다.** 상태를 바꾸는 스크립트가 좌석 버전을 하나 올리고, 알림에 그 번호를 싣는다. 클라이언트는 이미
  받은 번호보다 작은 알림을 버린다. 발행 경로나 순서에 기대지 않지만 WebSocket 계약(`SeatStatusEvent`)이 바뀐다.

## 4. 새 설계 후보

| | A. 지금 유지 | B. 상태는 스크립트, 순서만 락 | **C. 스크립트가 상태·장부·발행까지(추천)** | D. 락 없음 + 좌석 버전 |
| --- | --- | --- | --- | --- |
| 바뀌는 것 | 없음 | 선택·선점·해제 스크립트 보강. 발행이 있는 곳(L1~L3, L6, L7)만 락 유지 | 스크립트 보강 + 스크립트 안 `PUBLISH`. 락 패키지 삭제 | 스크립트 보강 + 이벤트에 `version`. 락 패키지 삭제 |
| 사용자당 Redis 왕복(03, 추정) | 약 21 | 약 12 | **4~5** | 4~5(+relay 발행 3) |
| 알림 순서 | 락으로 보장(서버 한 대 안에서. 여러 대는 ADR 0022처럼 락 안 동기 발행이 더 필요) | 락으로 보장 | Redis 실행 순서로 보장(서버 대수와 무관) | 클라이언트가 버전으로 맞춤 |
| WebSocket 계약 | 그대로 | 그대로 | 그대로(relay 메시지는 내부 형식, 구독자가 `SeatStatusEvent`로 바꿔 보낸다) | **바뀐다**(FE·gatling 수정) |
| D2-1(relay)과 관계 | ADR 0022 결정 1 그대로 | 그대로 | relay 구독자를 쓰고, 발행 위치만 Java 락 안 → 스크립트 안 | relay와 무관하게 동작 |
| D2-2(만료 장부)와 관계 | 장부 등록을 Lua에 넣는 결정과 별개 | 같음 | 같은 스크립트에서 상태 변경·장부 등록·발행을 함께 한다 | 같음 |
| 위험 | 지금 그대로 | 락과 스크립트가 섞여 이해하기 어렵다 | 스크립트가 길어지고 이벤트 메시지를 Lua에서 만든다. 스크립트 경쟁 테스트가 필수 | 클라이언트 구현에 기댄다 |
| 작업량(추정) | 0 | 1일 | 2~3일 | 2일 + FE |

**C를 추천하는 이유**

- 좌석 상태를 바꾸는 곳이 Redis 스크립트 하나로 모인다. "누가 먼저인가"를 Redis 하나가 정하므로 락·재확인·순서 규칙을 따로
  기억할 필요가 없다.
- D2-2에서 이미 "만료 장부 등록은 각 기능의 Lua 안에서 상태 변경과 함께 한다"고 정했다. 발행까지 같은 자리에 두면 규칙이 하나다.
- D2-1의 relay가 필요로 하는 순서 보장(ADR 0022의 "락 안에서 동기 `PUBLISH`")을 락 없이 더 단순하게 얻는다.
- 계약이 바뀌지 않는다. D는 C 뒤에도 더할 수 있다(전송 계층 순서까지 잡고 싶을 때).

## 5. C안: 좌석 상태 전이

좌석 하나의 Redis 상태는 셋이다. 비었음, 선택(회원 m), 선점(holdKey h). 주문 커밋 직후 잠깐은 선택과 선점이 함께 있다(후처리가
선택을 지운다. ADR 0001·0021 그대로).

| 전이 | 호출하는 곳 | 스크립트 안 조건 | 스크립트 안 쓰기 | 스크립트 안 발행 |
| --- | --- | --- | --- | --- |
| 선택 | 좌석 선택 API | 선택 키 없음, 선점 키 없음, 회원 한도 안 | 선택 키(TTL)·인덱스 2개, 만료 장부 등록 | `SELECTED` |
| 해제 | 좌석 해제 API, 일괄 해제 | 선택 키 = m | 선택 키·인덱스 삭제 | 지웠고 선점이 없으면 `DESELECTED` |
| 선택 만료 알림 | 만료 Worker(D2-2) | 선택 키 없음, 선점 키 없음 | 없음 | 비었으면 `DESELECTED` |
| 선점 | 주문 생성 | 모든 좌석의 선택 키 = m, 선점 키 없음 | 선점 키(TTL)·메타·인덱스, 만료 장부 등록 | 없음(주문 커밋 전이라 알리지 않는다) |
| 선점 확정 알림 | 주문 커밋 뒤 리스너 | 모든 좌석의 선점 키 = h | 그 좌석의 선택 키가 m이면 삭제 | `HELD` |
| 선점 해제 | 취소·만료 리스너, 주문 저장 실패 보상 | 좌석별 선점 키 = h | 그 좌석의 선점 키·인덱스, 메타 키 삭제 | 지웠고 선택·선점이 없으면 `RELEASED` |

- 발행 메시지는 relay 내부 형식(회차, 좌석, `performanceSeatId`, 동작, Redis 시각)이다. 구독자가 지금의 `SeatStatusEvent`로 바꿔
  같은 destination에 보낸다. `performanceSeatId`는 호출자가 이미 DB에서 읽은 값을 인자로 넘긴다.
- 재전달: 선점 확정 알림과 선점 해제는 조건이 안 맞으면 아무것도 하지 않으므로 다시 실행해도 안전하다(지금의 멱등성과 같다).
- 좌석 선택 API 앞의 빠른 확인(`SelectSeatUseCase.java:79`의 선점 `GET`)은 스크립트가 같은 확인을 하므로 뺄 수 있다.

## 6. 바뀌는 코드

- **없어짐**: `booking.concurrency` 패키지 전체(`DistributedLock`, `LockKey`, `LockOptions`, `LockScope`,
  `RedissonDistributedLock`, `RedissonLockKeyFormatter`)와 그 테스트, 네 곳의 `withLock`.
- **바뀜**
  - `RedissonSeatSelectionStore`: 선택 스크립트에 선점 확인·장부 등록·발행, 해제 스크립트에 발행.
  - `RedissonHoldStore`: 선점 스크립트에 본인 선택 확인·장부 등록, 해제를 스크립트로, 선점 확정 알림 스크립트 추가.
  - `SeatSelectionWriter`·`HeldSeatPublisher`·`HoldReleaser`: 락과 Java 쪽 재확인이 빠지고 스크립트 호출 하나가 된다.
  - `CreateOrderUseCase`: 선점 구간과 보상 해제의 락이 빠진다. 본인 선택 확인은 스크립트 결과로 판정한다.
  - `SeatStatusEventPublisher` 구현: 로컬 broker 대신 relay 구독자가 받은 메시지를 보낸다(D2-1).
- **함께 고를 것**: 선점 인덱스(`RSetCache`, `RedissonHoldStore.java:142`)를 선택 인덱스처럼 일반 Sorted Set으로 바꿀지.
  Redisson 만료 정리 작업(capacity-log P-014의 141ms 멈춤)이 없어지고, 점수도 Redis 시계로 맞춰진다.
- **그대로**: 주문 DB 트랜잭션 경계, 회원·회차 PENDING 유일 인덱스, Event Publication Registry 재시도, ADR 0001·0021의 업무 규칙.
- **gatling-test**: 판정의 "과부하(`E6003`) 1명 이상이면 FAIL"은 지금 락 대기 실패에서 나온다. 락이 없어지면 `E6003`을 내는 곳이
  사라지므로 판정 규칙을 함께 본다.
- **테스트**: `SeatContentionE2ETest`(같은 좌석 동시 주문), `SeatSelectionWriterTest`(알림 순서), `HeldSeatPublisherTest`,
  `HoldReleaserTest`, `CreateOrderUseCaseTest`, `CoreRedisIntegrationTest`. 스크립트는 Testcontainers Redis에서 위 3장의 경쟁 순서를
  하나씩 재현하는 테스트가 필요하다.

## 7. 락과 상관없이 남는 구멍

- **좌석 단위 DB 방어선이 없다.** Redis 재시작·장애로 선점을 잃으면(Core Redis 영속성 D1-4 미정) 좌석이 빈 것으로 보이고, 같은 좌석의
  PENDING 주문이 겹친다. 결제 확정(`Order.confirm()`)을 붙이면 이중 판매가 된다. 락은 이것을 막은 적이 없다. 결제 연결 전에 좌석 예약
  테이블이나 partial unique index로 막는 안을 따로 정한다([남은 작업](../todo.md)).
- **알림은 최대 한 번 전달이다.** Redis pub/sub은 끊긴 동안의 메시지를 다시 보내지 않는다. ADR 0022와 같고, FE 재연결 때 재조회(D2-5)로 메운다.
- **Lua 스크립트가 길어지면 그동안 Redis 전체가 멈춘다.** 좌석 수만큼 도는 스크립트(선점·해제)는 회원 한도(`max_hold_seat_count`)가
  상한을 지킨다. 회차 전체를 도는 스크립트는 만들지 않는다.
