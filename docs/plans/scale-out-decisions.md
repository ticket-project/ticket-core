# 스케일 아웃 결정 목록

작성 2026-10-25. Core를 여러 인스턴스로 늘리기 전에 정해야 할 것을 모은 작업 문서다. 2026-10-17 코드 리뷰의

[운영](../operations.md)·[예매 수명주기](../core-booking-lifecycle.md)로 옮기고 여기서는 상태만 바꾼다.

상태는 세 가지다.

- `미정`: 아직 논의하지 않았다.
- `추천 있음`: 추천안은 있지만 확정하지 않았다.
- `정함`: 확정했다. 옮긴 문서를 함께 적는다.

## 지금 상태(2026-11-03)

- 운영은 EC2 한 대(2 vCPU, 메모리 1.9GB)에 `ticket-be`, `ticket-redis`, `ticket-fe`, `ticket-nginx`, `datadog-agent`,
  `ticket-certbot` 컨테이너가 함께 떠 있다. 메모리가 작아 같은 호스트에 Core를 둘 띄울 수 없다. Core JVM에는 `-Xmx`가
  없다.
- DB는 RDS PostgreSQL이고 `max_connections`는 79다. Core 연결 풀은 Hikari 기본값 10, Tomcat 스레드는 200이다.
- D2-1·D2-2(relay, 좌석 락 삭제, 만료 처리)는 운영에 배포돼 있다(`46a8d7d0`).
- 운영 사다리에서 90 u/s는 PASS, 100 u/s는 FAIL이다. 막힌 곳은 호스트 CPU(P-017)이고 Datadog 프로파일러는 꺼 둔
  상태다(gatling-test capacity-log 2026-11-03-prod-profiler-off). 10-25의 60 u/s 교착(P-022)은 D0-2로 사라졌다.

## D0. 전제

### D0-1. 스케일 아웃의 목적과 목표 입장률

- **정할 것**: 늘리는 목적이 처리량인지, 가용성(한 대가 죽어도 서비스 유지)인지, 둘 다인지. 처리량이 목적이면 몇
  users/sec가 필요한지.
- **왜**: 목표가 없으면 몇 대가 필요한지, 서버 한 대 정리(D0-3)로 충분한지 판단할 수 없다. 가용성이 목적이면 처리량이
  충분해도 2대가 필요하다.
- **결정(2026-11-04)**: 처리량 + 확장 곡선. 같은 사양 Core 호스트를 1·2·3대로 재서 "늘린 만큼 처리량이 는다"와 그다음
  병목을 보인다. 운영은 2대로 두고 3대는 측정할 때만 띄운다. 가용성(한 대가 죽어도 유지)은 이번 범위에 넣지 않는다.
- **목표 숫자**: 2대가 1대의 1.7배 이상이면 합격이고, 못 미치면 병목을 찾는다. 1대 기준선은 2대와 같은 배치(Redis를
  Core 호스트 밖으로 뺀 뒤, D1-1)로 다시 잰다. 1.7배는 공유하는 Redis·DB 손실을 15%쯤 허용한 값으로 업계 기준값은
  아니다.
- **고른 이유**: 이 프로젝트의 목적은 "초당 몇 명을 견디는 시스템"이라고 근거 있게 내세울 숫자다. 대수별 곡선이 그 근거가
  되고, 인프라는 처리량만 볼 때와 같아 뒤 결정이 늘지 않는다.
- **고르지 않은 안**:
  - 처리량만(2대 한 번 측정): 가장 단순하지만 2대가 왜 그 배수인지 설명할 근거가 없다.
  - 처리량 + 가용성: nginx 이중화(관리형 LB), Redis 복제본과 자동 전환, 무중단 배포가 모두 필요해 결정과 비용이 두 배다.
    한 대가 죽으면 남은 대가 전부 받아야 해서 내세울 숫자도 작아진다. 필요해지면 그때 얹는다.
  - 목표 숫자 없이 측정값만: 결과가 낮아도 실패를 판단할 기준이 없다.
  - 절대 숫자(예: 200 u/s): 그 숫자 자체의 근거가 없다.

### D0-2. 60 u/s 멈춤(P-022) 수정 방식

- **결정**: B(`@Cacheable`의 `sync = true`를 뺀다). 2026-10-25 사용자가 골랐고 `43fe8873`로 master에 반영·배포했다.
  재측정에서 멈춤이 사라졌다(60 u/s는 CPU 포화로 FAIL).
- **고른 선택지**: gatling-test capacity-log 2026-10-25의 해결 선택지 A~E 중 B.
  - A. 판매 정책 캐시 조회를 트랜잭션 밖으로 옮긴다.
  - B. `@Cacheable`의 `sync = true`를 뺀다.
  - C. 미리 새로 고치는 캐시(`refreshAfterWrite`)로 바꾼다.
  - D. 캐시 유지 시간을 늘린다.
  - E. Hikari 연결 대기 시간 초과를 줄인다(보조 수단).
- **왜**: 인스턴스를 늘려도 이 교착은 인스턴스마다 그대로 생긴다. 대당 부하가 줄어 늦게 날 뿐이다. 그래서 스케일
  아웃과 별개로 먼저 고친다.

### D0-3. 호스트 배치(서버 한 대를 먼저 정리할지)

- **정할 것**: 인스턴스를 늘리기 전에 다음을 먼저 할지.
  - FE·Redis·Datadog Agent를 Core 호스트에서 분리한다.
  - 인스턴스 사양을 올린다.
  - JVM `-Xmx`를 정한다.
- **왜**: 호스트 CPU 0.94는 Core만이 아니라 함께 뜬 컨테이너 전체의 사용량이다. 분리나 사양 상향은 코드 변경 없이
  한계를 올릴 수 있다.
- **처음 추천**: 먼저 정리하고 다시 잰다. 스케일 아웃이 전제가 되고 D0-1이 확장 곡선으로 정해지면서, 질문이 "호스트가
  여러 대일 때 각 호스트에 무엇을 둘지"로 바뀌었다.
- **결정(2026-11-04)**: 지금 호스트를 앞단으로 쓴다(nginx·FE·certbot). Core는 새 전용 호스트에 Core와 Datadog Agent만
  둔다. Core 호스트는 지금과 같은 사양(2 vCPU, 1.9GB)으로 맞추고 사양 상향은 다루지 않는다. Redis 위치는 D1-1에서 정한다.
  - `-Xmx`는 정하지 않는다(기본값, 메모리의 1/4). 운영에서 쓰는 힙은 155~210MB로 상한 약 478MB의 절반이 안 되고, GC 멈춤은
    30초 실행당 0.1~0.6초다(gatling-test capacity-log 2026-10-19 운영 재측정, 2026-11-03 프로파일러 끔). 막히는 곳은 CPU다.
    측정에서 GC가 문제로 보이면 `-XX:MaxRAMPercentage`로 정한다.
- **고른 이유**: 모든 Core가 같은 조건(CPU를 혼자 씀)이어야 D0-1의 1.7배 판정과 대수별 곡선이 깨끗하다. 추가 EC2는
  아래 고르지 않은 안과 같은 2대다. 도메인·고정 IP·인증서가 지금 호스트에 남아 옮길 것이 없다.
  - 추후 ECS로 옮길 계획이다(2026-11-04 사용자). Core 전용 자리는 ECS의 Core 서비스와 같은 모양이고, 그때 앞단 EC2는
    ALB(경로 분배)와 ACM(인증서)으로 바뀐다. FE는 Next.js 서버(`next start`, `/api` rewrite)라 정적 호스팅으로 옮기려면 FE를
    고쳐야 해서 ECS 서비스로 둔다.
- **감수하는 것**: 앞단 호스트가 한 대라 죽으면 전체가 멈춘다(가용성은 D0-1에서 범위 밖). 앞단 CPU가 병목이 되는지 측정
  때 함께 본다.
- **고르지 않은 안**: 지금 호스트에 Core를 남기고 Core 호스트 1대 추가. 옮기는 작업은 적지만, 지금 호스트의 Core는
  nginx·FE와 CPU를 나눠 써서 먼저 막히고 1대 기준선을 어느 호스트로 잴지 애매하다. ECS로 갈 때 다시 뜯어야 한다.

## D1. 인프라

### D1-1. Redis를 어디에 둘지

- **정할 것**: 모든 Core 인스턴스가 함께 쓸 Redis의 위치와 종류.
- **왜**: 선택·선점·락·토큰·좌석 알림 relay가 모두 Redis에 있다. 지금 Redis는 Core와 같은 호스트에 있어서, 다른
  호스트의 Core가 붙으면 그 호스트가 장애 지점이 되고 CPU도 나눠 쓴다.
- **선택지**:
  - 지금 호스트의 Redis에 다른 Core가 네트워크로 붙는다. 가장 쉽지만 위 문제가 그대로다.
  - 별도 EC2에 Redis를 둔다. 지금과 같은 설정을 쓸 수 있다.
  - ElastiCache 단일 노드를 쓴다. D2-2 구현으로 keyspace 알림과 기동 시 `CONFIG SET`이 없어져 파라미터 그룹 설정이
    필요 없다.
  - Redis Cluster는 쓰지 않는다. hold 메타 키(`hold:key:*`)에 hash tag가 없고, 좌석 선택 Lua가 회차 키(`{perf:N}`)와 전역
    장부(`seat:select:expiry`)를 함께 써서 CROSSSLOT 오류를 낸다. ElastiCache Serverless도 hash slot 단위라 같은 이유로
    쓸 수 없다.
- **함께 볼 것(2026-11-04)**: 추후 ECS로 가면 앞단 EC2가 없어질 수 있다(D0-3). Redis를 컨테이너로 두면 재시작 때 좌석
  hold가 사라진다.
- **결정(2026-11-04)**: 앞단 호스트(지금 호스트)의 Redis를 그대로 쓰고 Core 호스트들이 네트워크로 붙는다.
  - 해야 할 것: 보안 그룹으로 Core 호스트에서 오는 6379 접속만 허용하고(인터넷에는 열지 않는다) Redis에 비밀번호를
    건다. 지금 운영 Redis에 비밀번호가 있는지는 저장소 밖 compose라 확인하지 못했다.
- **고른 이유**: 지금 할 일과 추가 비용이 가장 적다. 직접 운영하는 Redis라 AOF를 켤 수 있어 D1-4의 선택지가 넓다. ECS로
  갈 때 옮기는 비용은 접속 주소 변경과 판매 없는 시간의 재시작이고, hold는 몇 분짜리라 옮길 데이터가 거의 없다.
- **감수하는 것**: 앞단의 nginx·FE와 CPU를 나눠 쓴다. 3대 측정(약 270 u/s)에서도 작다고 보지만(추정) 측정 때 앞단 CPU를
  함께 본다. ECS로 갈 때 한 번 옮긴다.
- **고르지 않은 안**: ElastiCache 노드형(ECS 때 안 옮기고 관리가 적지만 비용이 들고 AOF가 없다), Redis 전용 EC2(CPU를
  나눠 쓰지 않는 것 말고는 A보다 얻는 것이 작고 관리할 호스트가 는다).
- **추천**: Core 호스트 밖의 단일 노드(별도 EC2 또는 ElastiCache). 그 다음 확장 순서는 D1-5에서 정한다.

### D1-2. 요청을 어떻게 나눌지(LB)

- **정할 것**: 지금 nginx에 upstream을 여러 개 두는지, ALB 같은 관리형 LB로 바꾸는지. Core를 같은 호스트에 여러 개
  띄우는지, 호스트를 늘리는지.
- **왜**: 같은 호스트에 Core 컨테이너를 2개 띄우면 CPU가 늘지 않는다. 처리량이 목적이면 호스트가 늘어야 한다.
- **선택지**:
  - 같은 호스트에 Core 컨테이너 2대: 비용이 들지 않고 무중단 배포와 2대 정합성(D2)을 검증할 수 있다. 처리량은 거의
    늘지 않는다.
  - EC2 여러 대와 ALB.
  - ECS.
  - 같은 호스트 2대는 메모리(1.9GB)가 모자라 쓸 수 없다. 추후 ECS로 옮길 계획이다(D0-3). ECS는 배포마다 작업 IP가 바뀌어
    nginx upstream보다 ALB와 맞는다.
- **함께 볼 것**: 상태 확인은 `/actuator/health/readiness`를 쓴다(probe는 이미 켜져 있다). nginx의
  `worker_connections`·`limit_req`는 노드마다 따로 적용된다.
- **처음 추천**: 앞단 nginx에 upstream을 추가하는 것이 가장 작은 변경이다. ALB는 ECS로 갈 때 들인다.
- **결정(2026-11-09)**: 스케일 아웃 때 ALB를 들인다.
  - `/api/*`·`/ws/*`는 Core 대상 그룹(Core 호스트 2대)으로, 나머지는 FE로 보낸다. 인증서는 ACM으로 ALB에서 끝낸다.
  - 상태 확인은 `/actuator/health/readiness`. 분배는 기본(라운드 로빈). sticky는 두지 않는다(D2-3 쿠키, D2-4).
  - 대상 그룹 대기 시간(deregistration delay)은 기본 300초를 Spring 종료 대기에 맞춰 약 40초로 줄인다(D4-1).
  - ALB 유휴 시간(기본 60초)은 SockJS의 25초 신호가 연결을 살려 둔다(D2-4).
- **고른 이유**: ECS로 가면 태스크 IP가 배포마다 바뀌어 ALB가 필요하므로 한 번에 들인다. ALB가 주기적으로 상태를 확인해
  고장 난 서버를 빼고, 롤링 때 빼고 넣기를 대상 그룹 등록·해제로 한다(nginx 설정 수정·reload 스크립트가 필요 없다).
- **감수하는 것**: 비용(시간 요금 + 사용량, 월 2만~3만 원대 추정). 도메인을 ALB로 옮기고 인증서를 ACM으로 바꾸는 작업.
  앞단 호스트(Redis, D1-1)가 하나라 가용성은 그대로다.
- **고르지 않은 안**:
  - 앞단 nginx upstream: 가장 작은 변경이지만 상태 확인이 수동적이고 롤링 스크립트를 직접 짜야 하며 ECS 때 다시 바꾼다.
  - DNS로 나누기: 고장 난 서버를 빼지 못하고 DNS 캐시 때문에 늦게 반영된다.
- **함께 정리할 것**: ALB 구성 때 앞단 호스트 nginx·certbot의 역할(FE를 ALB가 바로 보낼지)을 정한다. Queue
  (`queue.oneticket.site`)는 범위 밖이다.

### D1-3. 어떻게 배포할지

- **정할 것**: 여러 인스턴스를 어떤 순서로 바꿀지.
- **왜**: [배포 workflow](../../.github/workflows/deploy.yml)는 컨테이너 이름 `ticket-be` 하나, 서버 한 대, 배포 뒤
  nginx 재시작을 전제로 한다.
- **추천**: 한 대씩 LB에서 빼고, 바꾸고, readiness가 UP이면 다시 넣는다. graceful shutdown 대기 시간과 WebSocket
  재연결이 한꺼번에 몰리는 것을 함께 본다.
- **readiness·liveness 분리**: 지금 workflow는 `/actuator/health` 하나로 배포 성공을 판단한다. LB에 넣을지는
  `/actuator/health/readiness`, 컨테이너를 다시 띄울지는 `/actuator/health/liveness`로 나눌지 정한다.
- **결정(2026-11-09)**: 롤링으로 한다. 한 대씩 ALB 대상 그룹에서 빼고(D1-2), 새 버전으로 바꾸고, 준비되면 다시 넣는다. ECS로 가도
  ECS 서비스의 기본 배포(롤링)로 시작한다. 빼는 방법·readiness 경로·대기 시간은 구현 때 D4-1 종료 설정과 함께 정한다.
- **고른 이유**: 서비스가 멈추지 않고 서버가 더 필요 없다. 블루/그린도 DB·Redis는 두 버전이 함께 쓰므로 D4-1 호환
  규칙이 거의 그대로 필요해, 서버를 두 배로 쓰는 만큼 얻는 것이 적다. ECS 기본 방식과 같아 규칙이 그대로 이어진다.
- **감수하는 것**: 몇 분 동안 옛 버전과 새 버전이 함께 돌아 D4-1 규칙을 전부 지켜야 한다. 내리는 서버의 WebSocket은
  끊기고 FE가 5초 뒤 다른 서버로 다시 붙는다. 한 대를 바꾸는 동안 남은 한 대가 요청을 모두 받는다.
- **고르지 않은 안**:
  - 블루/그린: 배포 중 서버가 두 배(2대면 4대, D3-2 상한 4대에 딱 맞고 3대부터 넘는다). EC2에서는 인스턴스를 더 띄우고
    전환하는 스크립트가 필요하다. ECS로 간 뒤 다시 볼 수 있다.
  - 전부 내렸다 올리기(지금 방식): 호환 규칙은 거의 필요 없지만 배포마다 기동 시간(2026-11-09 152초)만큼 멈춘다.
  - 카나리: 2대에서는 첫 한 대를 바꾼 상태가 50% 카나리라 따로 두지 않는다.

### D1-4. Core Redis 영속성

- **정할 것**: Core Redis에 AOF를 켤지, 메모리가 찼을 때 `noeviction`을 쓸지.
- **왜**: Core Redis는 좌석 hold를 담는다. 재시작으로 데이터를 잃거나 메모리 부족으로 키가 밀려나면, 주문은 PENDING인데
  좌석은 빈 것으로 보인다. 좌석 단위 DB 방어선이 아직 없어서([남은 작업](../todo.md)의 "좌석 단위 DB 방어선") 이 손실은
  겹친 PENDING 주문으로 이어질 수 있다.
- **함께 볼 것**: ticket-queue는 부하 테스트 격리 때문에 AOF를 껐다. Core는 저장하는 데이터가 달라서 그 설정을 따라가지
  않는다. ElastiCache는 Valkey와 Redis OSS 2.8.22 이후 버전에서 `appendonly`를 지원하지 않는다(AWS ElastiCache API
  문서 `CacheCluster`). ElastiCache로 가면 대책은 복제본과 좌석 단위 DB 방어선이다.
- **결정(2026-11-04)**: AOF `everysec`를 켜고, 메모리가 차면 `noeviction`으로 새 쓰기를 거절하며 `maxmemory` 상한을 둔다.
  상한 값은 적용할 때 운영 `INFO memory`로 지금 사용량을 보고 정한다. 설정은 저장소 밖 운영 compose에 둔다(`appendonly yes`,
  `appendfsync everysec`, `maxmemory`, `maxmemory-policy noeviction`, `/data` 볼륨).
- **고른 이유**: 잃으면 가장 위험한 것은 좌석 hold다(겹친 PENDING 주문). AOF `everysec`는 재시작 때 잃는 폭을 최대 1초로
  줄이고 비용이 작다. 밀어내기 정책은 hold를 조용히 지우므로 쓰지 않는다. 상한이 없으면 FE·nginx와 함께 쓰는 앞단
  호스트(1.9GB)의 메모리를 다 써서 다른 컨테이너까지 죽을 수 있다.
- **감수하는 것**: 메모리가 차면 좌석 선택·선점이 오류로 실패한다. AOF는 손실 확률을 줄일 뿐 막지 못한다. 이중 판매를
  막는 것은 좌석 단위 DB 방어선이고 결제를 붙이기 전에 따로 정한다.
- **고르지 않은 안**: 저장 안 함(재시작하면 전부 잃는다), RDB 스냅샷만(마지막 스냅샷 이후 몇 분치를 잃는다), AOF
  `always`(판매 순간 모든 쓰기가 디스크를 기다린다), `volatile-lru` 등 밀어내기(hold가 조용히 사라진다).

### D1-5. Redis 확장 순서

- **정할 것**: Core 호스트 밖으로 옮긴 뒤(D1-1) Redis를 어떤 순서로 키울지.
- **예상 순서**: 복제본과 자동 failover → 용도별 분리(좌석, 인증 토큰, 알림) → 클러스터.
- **함께 볼 것**: 좌석 키는 모두 `{perf:N}` hash tag라서, 클러스터에서도 회차 하나의 부하는 서버 한 대로 간다. 인기 회차
  하나의 한계는 클러스터로 올라가지 않는다. D2-2를 구현하면 keyspace 알림을 쓰지 않아 노드별
  구독은 필요 없지만, 좌석 선택 만료의 전역 장부를 회차별 장부와 회차 목록으로 바꿔야 한다(D2-2).

## D2. 늘리자마자 기능이 깨지는 것(P0)

### D2-1. 좌석 알림을 모든 인스턴스에 나누는 방법

- **문제**: `WebSocketConfig`의 simple broker는 같은 서버에 붙은 사용자에게만 보낸다. 서버 A가 보낸 `SELECTED`·`HELD`·
  `RELEASED`를 서버 B의 사용자는 받지 못한다.
- **선택지**: Redis pub/sub relay, 외부 STOMP 브로커(RabbitMQ 등), Redis Streams.
- **결정(2026-10-26)**: Redis pub/sub relay. 좌석 상태를 바꾼 인스턴스가 Redis 채널에 동기로 발행하고, 모든
  인스턴스가 구독 연결 하나와 단일 스레드로 받아 자기 사용자에게 보낸다. 발행 순서 보장과 WebSocket 계약이 그대로
  유지된다. 상세는 [ADR 0022](../adr/0022-seat-status-relay-and-single-expiration-claim.md) 결정 1.
  - 다시 확인(2026-10-26): 구현을 되돌린 뒤 relay 없이 두는 안과 다시 비교해 relay로 정했다. FE는 좌석 상태를 화면에
    들어올 때 한 번만 불러오고, 그 뒤로는 WebSocket 알림으로만 화면을 바꾼다(주기 재조회·재연결 재조회·창 포커스 재조회
    없음). relay가 없으면 다른 서버에서 생긴 선택·선점·해제를 새로고침 전까지 못 보고, 서버가 늘수록 못 보는 몫이 커진다.
  - 고른 이유: 이미 쓰는 Redis로 되어 운영할 인프라가 늘지 않는다. 구독이 끊긴 동안의 메시지는 사라지지만, 사용자의
    WebSocket이 끊긴 동안의 알림도 어차피 놓치므로 둘 다 FE 재조회(D2-5)로 메운다. D2-2의 좌석 선택 만료 알림도 이
    relay로 보낸다.
  - 고르지 않은 안: 외부 STOMP 브로커(RabbitMQ 등, Spring `enableStompBrokerRelay`)는 구독 관리를 브로커가 맡지만
    운영할 서버가 늘고, 사용자 접속마다 브로커 TCP 연결을 연다. Redis Streams는 인스턴스 구독이 끊겨도 이어 읽지만
    사용자 쪽 유실은 그대로라 재조회가 어차피 필요하고, 읽은 위치와 정리(trim) 관리가 는다. 회차별로 서버를 고정하면
    relay가 필요 없지만, 인기 회차 하나에 사용자가 몰리는 서비스라 그 서버 한 대에 부하가 몰린다.
- **세부 결정**:
  - 채널 단위(2026-10-26 정함): 채널 하나를 모든 인스턴스가 구독한다. 인스턴스는 받은 알림을 그 회차 destination으로
    보내고, 그 회차 구독자가 없으면 simple broker가 버린다. 구독을 켜고 끄는 관리가 없다.
    - 회차별 채널(`{perf:N}` hash tag, 자기 접속자가 보는 회차만 동적 구독)은 고르지 않았다. 필요한 알림만 받지만 구독을
      켜고 끄는 코드가 필요하고, 구독을 켜는 순간 직전 알림을 놓칠 수 있다. Redis가 한 대인 지금은 얻는 것이 작다.
    - 함께 볼 것: Redis를 클러스터 모드로 옮기면 일반 `PUBLISH`가 모든 노드로 퍼지고, 상태를 바꾸는 Lua 안에서 발행하면
      회차 노드 안의 sharded pub/sub(`SPUBLISH`, 패턴 구독 불가)이 필요하다. 그때 회차별 채널을 다시 본다(D1-5).
  - relay 큐(2026-10-26 정함): 전달 스레드 하나만 두고 큐에 상한을 두지 않는다. 순서를 지키려고 스레드는 하나다.
    - 감수하는 것: 전달이 밀리면 큐가 메모리에 계속 쌓일 수 있다. 밀림은 executor 큐 지표(`executor_queued_tasks`,
      Spring Boot가 `ThreadPoolTaskExecutor` 빈마다 자동으로 붙인다)로 본다.
    - 상한을 두고 넘치면 버리며 경고 로그·지표를 남기는 안(ADR 0022 원래 문구)은 고르지 않았다. 메모리는 지키지만 버린
      알림이 생기고, 상한 값과 버릴 때의 처리를 정해야 한다. 넘칠 때 받는 스레드가 직접 처리하는 방식(`CallerRunsPolicy`)은
      Redis 수신 스레드를 막고 순서를 깨므로 어느 경우에도 쓰지 않는다.
  - 발행 위치(2026-10-26 정함): 상태를 바꾸는 Lua 스크립트 안에서 `PUBLISH`한다. Redis가 스크립트를 하나씩 실행하므로
    락 없이도 알림 순서가 상태 변화 순서와 같다. 받는 쪽(구독 → 전달)은 Java 발행과 같다.
  - 좌석 락(2026-10-28 정함): 걷어낸다. [좌석 분산 락 다시 설계하기](seat-lock-redesign.md)의 C안(상태 변경·만료 장부 등록·
    발행을 스크립트 하나에서)으로 간다. 선택·해제·선점·선점 확정 알림·선점 해제·선택 만료 알림이 각자 스크립트 하나가
    되고, 좌석 락 패키지(concurrency)가 없어진다.
    - 고른 이유: "확인하고 보내기"를 Redis가 한 줄로 세워, 서버 대수와 무관하게 알림 순서가 상태 변화 순서와 같다. 좌석 선택
      Lua를 장부 등록(D2-2) 때문에 어차피 고친다. 사용자당 Redis 왕복이 약 21번에서 4~5번으로, Core CPU가 약 10% 줄
      것으로 본다(둘 다 추정, 측정은 구현 뒤). 락 대기 실패(`E6003`)가 사라진다.
    - 감수하는 것: 스크립트가 길어지고 알림 메시지를 Lua에서 만든다. 경쟁 순서를 하나씩 재현하는 Testcontainers Redis
      테스트가 필요하다. 작업량 2~3일(추정). gatling-test 판정의 "과부하(`E6003`) 1명 이상이면 FAIL"을 함께 고친다.
    - 고르지 않은 안: 좌석 락 안에서 relay로 보내기(2026-10-26에 구현했다 되돌린 `96036b8e`, 작업은 작지만 락과 왕복이
      그대로다), 상태는 스크립트·발행 있는 곳만 락(락과 스크립트가 섞인다), 좌석마다 버전 번호(WebSocket 계약이 바뀌어
      FE를 고쳐야 한다).
  - 좌석 선점 인덱스(2026-10-28 정함): `RSetCache`를 선택 인덱스와 같은 일반 Sorted Set으로 바꾼다(좌석 락 재설계 8장 3).
    좌석 키·장부·인덱스가 모두 Redis 시계 하나를 쓰고, Redisson 만료 정리 작업이 없어진다.
    - 좌석 락 안의 Java에서 동기로 `PUBLISH`하는 안은 고르지 않았다. 바꿀 곳은 적지만 락을 잡은 시간이 Redis 왕복만큼
      늘고, 좌석 락에 계속 기대게 된다.

### D2-2. Redis 만료 알림 중복 처리

- **문제**: Redis는 키를 지울 때 "이 키 지웠어"라고 구독자 모두에게 방송한다. 인스턴스가 N대면 모두가 듣고 모두가
  처리한다.
  - 주문 선점 만료: 주문을 `EXPIRED`로 바꾼다. 결과는 한 번만 반영되지만 DB 연결과 lock 대기를 N배로 쓴다.
  - 좌석 선택 만료: "좌석 비었어요"(`DESELECTED`)를 보낸다. 좌석 확인과 좌석 락 경합이 N배이고, D2-1을 하면 같은
    알림이 N번 나간다.
  - 알림은 보내고 끝이라 구독이 끊긴 동안의 알림은 사라지고, 키를 실제로 지울 때 나가서 TTL 시각보다 늦을 수 있다.
    관리형 Redis는 기동 시 `CONFIG SET`이 막히고, 클러스터는 노드마다 따로 구독해야 한다.
- **선택지**: 지금 그대로(알림 + 청소), 알림 없이 DB 주기 청소, Redis 지연 큐(만료 예정 Sorted Set 장부) + Worker,
  외부 메시지 큐의 지연 배달, 주문을 만든 서버의 메모리 타이머 + 청소, Quartz 클러스터, DB 안의 pg_cron, 읽을 때 판정.
- **결정(2026-10-28)**: Redis 만료 알림을 쓰지 않는다. 각 만료는 자기 정보가 있는 저장소에서 처리한다.
  - **주문 선점 만료: 알림 없이 짧은 주기 DB 청소.** `HoldKeyExpirationHandler`를 지우고 `OrderExpirationTrigger`가
    짧은 주기로 만료 시각이 지난 PENDING 주문을 찾아 주문마다 행 락 → `EXPIRED` → 커밋한다. 같은 주문은 한 인스턴스만
    처리한다(아래 세부 결정).
    그 뒤는 지금과 같다(`OrderTerminated` → `HoldReleaser` → `RELEASED`). 좌석은 hold 키 TTL로 제때 풀린다.
  - **좌석 선택 만료: Redis 장부 + Worker + relay.** 좌석 선택 Lua(`SELECT_IF_ABSENT_SCRIPT`)가 선택 키를 쓸 때 장부
    (Sorted Set, 값 "회차:좌석", 점수 만료 시각)에도 같이 쓴다. Worker가 짧은 주기로 시각이 지난 항목을 Lua 한 번으로
    꺼내므로 한 인스턴스만 처리한다. 좌석이 비어 있으면 같은 Lua 안에서 relay 채널(D2-1)에 `DESELECTED`를 `PUBLISH`한다.
  - 두 쪽을 다 하면 `RedisExpirationListenerConfig`(keyspace 알림 구독과 기동 시 `CONFIG SET`)를 지운다.
- **고른 이유**:
  - 주문은 정보가 DB에 있으므로 DB만 보고 정한다. PENDING으로 남는 한 다음 주기에 다시 잡혀 유실이 없고, 인스턴스
    수만큼 일이 늘지 않는다. 사용자 구현 계획 3.2와도 같다.
  - 좌석 선택은 정보가 Redis에만 있으므로 장부도 Redis에 두면 선택 Lua 안에서 함께 쓰여 둘이 어긋나지 않는다. 주문에서
    장부를 되돌린 이유(Redis 장부와 DB 주문이 어긋남)가 여기에는 없다. 알림이 Redis 삭제 시점이 아니라 만료 시각에
    나가고, 구독이 끊겨도 장부에 남는다. FE가 좌석을 다시 조회하지 않아(D2-5) 빠진 `DESELECTED`가 새로고침 때까지 남으므로
    알림의 신뢰성이 중요하다. "비어 있으면 발행"이 Lua 하나라 확인과 발행 사이에 다른 상태 변경이 끼지 못한다.
  - 두 쪽 모두 알림을 쓰지 않으므로 관리형 Redis 설정(D1-1)과 클러스터 노드별 구독(D1-5)이 필요 없어진다.
- **감수하는 것**:
  - 주문 `EXPIRED` 반영, 같은 회원의 재주문(그동안 E5004), `RELEASED` 알림이 최대 청소 주기만큼 늦다.
  - 좌석 선택 장부와 Worker 코드가 는다. 꺼낸 뒤 처리 전에 인스턴스가 죽으면 그 알림만 빠진다(화면 알림뿐이다).
  - 전역 장부는 선택 키(`{perf:N}`)와 다른 슬롯이라 Redis 클러스터에서는 한 Lua로 쓸 수 없다. 클러스터로 갈 때 회차별 장부와
    회차 목록으로 바꾼다(2026-10-26 설계, 커밋 `cde8a578`).
  - 사용자 구현 계획 2.1("별도의 좌석 선택 만료 스케줄러를 두지 않는다")·2.2("keyspace `expired` 이벤트를 사용한다")와
    다르다.
- **고르지 않은 안**:
  - 지금 그대로: 코드는 0줄이지만 N배 작업, 알림 유실 시 최대 5분, Redis 설정 의존이 남는다.
  - 좌석 선택 알림 + 각 인스턴스가 자기 접속자에게만 전송(사용자 구현 계획 2.3): 코드가 가장 적지만 좌석 확인이 N배이고,
    확인과 전송 사이에 다른 사용자가 고르면 `DESELECTED`가 `SELECTED`보다 늦게 도착할 수 있다.
  - 좌석 선택 알림 + claim + relay(2026-10-26 정했다가 되돌림): 한 대만 처리하지만 알림 유실과 Redis 설정 의존이 남는다.
  - 주문 장부 + Worker(2026-10-26 구현했다가 되돌림): Redis 장부와 DB 주문이 어긋나는 경우를 따로 막아야 한다.
  - 메시지 큐 지연 배달(SQS·RabbitMQ): 운영할 인프라가 늘고, SQS 지연은 최대 15분이다.
  - 메모리 타이머 + 청소: 즉시 처리되지만 배포 때마다 예약이 사라지고 코드가 B보다 많다. 청소 주기가 길다는 근거가
    생기면 주문 쪽에 얹는다.
  - Quartz 클러스터: 주문마다 작업 행을 쓰고 테이블 11개가 는다.
  - pg_cron: 앱을 거치지 않아 `OrderTerminated`·Redis 정리·`RELEASED`가 나가지 않는다.
  - 읽을 때 판정: 유일 인덱스와 `RELEASED`가 DB 상태를 따르므로 단독으로는 부족하다.
- **세부 결정**:
  - 주문 청소의 중복 방지(2026-10-28 정함): 모든 인스턴스가 청소하고, 주문 한 건마다 트랜잭션을 열어
    `FOR UPDATE SKIP LOCKED`로 다른 인스턴스가 잠그지 않은 만료 주문 하나를 잠가 처리한다. 다른 인스턴스가 잠근 주문은
    기다리지 않고 건너뛰므로 같은 주문을 두 번 처리하지 않는다. 계속 실패하는 주문을 같은 실행에서 다시 잡지 않도록
    `id > 이번 실행에서 마지막으로 본 id`를 함께 건다.
    - 고른 이유: 청소가 주문 만료의 유일한 경로라, 인스턴스 한 대라도 살아 있으면 기다림 없이 계속되어야 한다. 실행하던
      인스턴스가 죽으면 DB가 롤백하며 잠금을 풀어 다른 인스턴스가 다음 조회에서 잡는다. 만료가 몰리면 인스턴스들이
      나눠 처리한다. 새 의존성·테이블·락 유지 시간 값이 없고, 주문마다 따로 트랜잭션(사용자 구현 계획 3.5)과 맞는다.
    - 감수하는 것: 인스턴스마다 주기마다 조회가 나간다. 사용자 구현 계획 3.3·3.4("한 대만 실행", Redis 분산 락)와
      글자 그대로는 다르고, 목적(중복 처리 없음)은 지킨다. `EventPublicationMaintenance`의 중복 실행(D3-1)은 따로 정한다.
      Hibernate의 SKIP LOCKED 힌트가 PostgreSQL에서 `SKIP LOCKED`로 나가는지는 구현 때 확인한다.
    - 고르지 않은 안: ShedLock JDBC(실행 인스턴스가 죽으면 락 유지 시간만큼 늦고 의존성·테이블이 는다, 2026-10-26 구현했다가
      되돌림), `worker.enabled`를 한 대에만 켜기(그 한 대가 내려가면 만료가 멈춘다), Redis 분산 락(DB만 보는 작업이 Redis
      장애에 묶인다).
  - 주문 유효성의 기준(2026-10-28 정함): 주문이 살아 있는지는 상태(`status`)가 아니라 만료 시각(`expires_at`)으로 정한다.
    주문을 쓰는 곳(결제 확정, 취소, 상태 조회)은 상태가 PENDING이어도 지금 시각이 만료 시각을 지났으면 끝난 주문으로
    다룬다. 결제 확정은 거절, 취소는 "이미 끝난 주문" 거절, 상태 조회는 `EXPIRED`로 보여 준다. DB 상태를 `EXPIRED`로
    바꾸는 일은 청소만 한다(사용자 구현 계획 3.1). 예외는 아래 "만료된 주문이 새 주문을 막을 때" 하나다.
    - 고른 이유: 만료 시각과 청소 사이에는 상태가 아직 PENDING이다. 그 사이 hold 키는 TTL로 풀려 다른 사용자가 같은 좌석을
      주문할 수 있으므로, 상태만 보고 결제를 받으면 이중 판매가 된다. 청소 주기를 줄여도 틈은 남고, 쓰는 순간 시각을
      비교하면 틈이 없다. 그래서 청소 주기는 정확성과 무관해지고, 표시와 알림이 얼마나 늦어도 되는지만 정한다.
    - 함께 정할 것: 결제 승인 요청이 만료 직전에 나가 응답이 만료 뒤에 오는 경우(아래 남은 것).
    - 상태 조회 응답이 바뀌므로 공개 API 계약 변경이다. FE가 값을 어떻게 쓰는지 확인한다.
  - 청소 주기와 실행당 상한(2026-10-28 정함): 기본 5초(설정값, 부하 테스트로 조정), 실행당 상한은 두지 않고 끝까지
    처리한다. 스케줄러 스레드는 기본값(1개)을 그대로 둔다.
    - 고른 이유: SKIP LOCKED로 주문을 한 건씩 처리하므로 서버당 메모리는 한 건, DB 연결은 하나만 쓰고 트랜잭션도 짧다.
      사용자 구현 계획 3.7이 상한으로 막으려던 메모리·연결 풀 고갈과 장시간 점유가 생기지 않는다. 상한을 두면 쌓인 주문이
      늦게 비워지고, 실패를 상한에 세면 앞쪽 실패가 뒤쪽을 막는다. 주기는 위 기준 덕분에 정확성과 무관하다.
    - 감수하는 것: 청소와 `EventPublicationMaintenance`가 서버마다 스케줄러 스레드 하나를 같이 써서 한쪽이 길면 그
      서버에서 다른 쪽이 기다린다. 청소는 다른 서버가 계속하고, 재처리는 원래 재시도 작업이다. 서로 밀리는 것이 지표로
      보이면 `spring.task.scheduling.pool.size`를 2로, 그래도 부족하면 시간 상한을 둔다. 계획 3.7("N은 설정값")과 다르다.
  - 결제 마감(2026-10-28 정함, 결제가 붙는다고 가정): 결제는 승인까지 주문 만료 시각 안에 끝나야 하고, 넘으면 취소한다.
    결제 페이지에 들어갈 때 시간을 늘려 주지 않는다.
    - 승인 요청 직전에 만료 시각을 확인하고, 지났으면 승인을 요청하지 않는다(돈이 나가지 않는다).

    - 승인 결과를 모르는 결제(응답 시간 초과, 그 사이 인스턴스 장애)는 나중에 PG 결제 조회로 확인해, 승인됐고 만료

    - 확정할 때는 시각과 함께 좌석이 아직 이 주문의 것인지 확인한다(서버 시계 차이, [남은 작업](../todo.md)의 좌석 단위

    - 고른 이유: 이미 정한 "주문 유효성은 만료 시각"과 규칙이 하나로 맞고, FE를 고치지 않아도 화면 타이머와 실제 마감이

      제한 시간을 두고 넘으면 티켓을 다시 판매로 돌린다.
    - 감수하는 것: 승인 요청이 만료 직전 몇 초에 걸치면 "결제됐다가 자동 취소"가 생긴다.
    - 고르지 않은 안: 결제 페이지에 들어가면 hold와 주문 시간을 늘리고 "결제 중" 상태를 두는 안(seats.io가 결제 페이지 진입 때

      본다.

      빼기(2026-10-19에 걷어낸 회원·회차 분산 락이 다시 필요하다). 부분 인덱스 조건에는 지금 시각을 넣을 수 없다.
  - 좌석 선택 장부 키(2026-10-28 정함): 전역 Sorted Set `seat:select:expiry` 하나. 값은 "회차 id:좌석 id", 점수는 좌석 선택
    Lua가 Redis `TIME`으로 계산하는 선택 만료 시각(밀리초)이다. Worker도 "지금"을 Redis `TIME`으로 잡아 시계가 Redis
    하나다. 같은 좌석을 다시 고르면 항목이 늘지 않고 점수만 바뀐다. 클러스터로 갈 때 회차별 장부로 바꾼다(위 감수하는 것).
  - 좌석 선택 Worker(2026-10-28 정함): 모든 인스턴스가 1초마다 점수가 지금 이하인 항목을 Lua 한 번으로 최대 100개 꺼내며
    지운다. 같은 항목을 두 인스턴스가 꺼내지 않는다. 100개를 꽉 채워 꺼냈으면 바로 다시 꺼낸다. 꺼낸 좌석이 비어 있으면
    relay로 `DESELECTED`를 보낸다. 꺼낸 뒤 처리 전에 인스턴스가 죽으면 그 알림은 버린다(화면 알림뿐이다).
    - 고르지 않은 안: 한 인스턴스만 꺼내기(그 한 대가 죽으면 멈춘다), 더 짧은 주기(Redis 호출만 는다), 꺼낸 항목을 처리 중
      목록에 두었다가 되살리기(화면 알림 하나를 위해 장치가 는다).
  - 좌석 해제·주문 생성 때 장부 항목(2026-10-28 정함): 지우지 않는다. Worker가 꺼낼 때 좌석이 비어 있는지 확인하므로,
    해제한 좌석은 만료 시각에 `DESELECTED`가 한 번 더 나가고(화면은 같다) 선점으로 넘어간 좌석은 보내지 않는다. 지우면
    해제·주문 생성 경로에 Redis 명령이 하나씩 는다.
  - 관측 지표(2026-10-28 정함, 사용자 구현 계획 6절): 볼 지표만 정하고 임계값은 구현·부하 측정 뒤에 정한다.
    - 청소 지연: 만료 시각이 지났는데 아직 PENDING인 주문 수와 가장 오래 밀린 시간. 청소 주기가 충분한지 본다.
    - 좌석 장부 적체: 시각이 지났는데 아직 꺼내지 않은 장부 항목 수. `DESELECTED` 지연을 본다.
    - relay 전달 큐: 인스턴스별 relay 전달 executor의 `executor_queued_tasks`. 상한 없는 큐가 쌓이는지 본다.
    - 늦은 승인 자동 취소: 승인 응답이 만료 뒤에 와 결제를 취소한 건수(결제를 붙인 뒤). 늘면 결제 페이지 진입 때 연장을
      다시 본다.
    - 좌석 전체 재동기화 주기는 FE를 고칠 수 없어 보류하고(D2-5), Redis 클러스터 대응은 D1-5에서 정한다.
  - Worker의 꺼내기와 "비어 있으면 `DESELECTED` 발행"은 같은 스크립트에서 할 수 있다(D2-1 좌석 락 결정). 그러면 꺼낸 뒤
    처리 전에 죽어 알림이 빠지는 틈도 없어진다. 구현 때 스크립트 길이(한 번에 100개)를 보고 정한다.
  - 2026-10-26에 정한 좌석 선택 claim(`SET expired-claim:... NX PX 60000`, 위치·TTL 60초)은 이 결정으로 대체됐다. 내용은
    커밋 `ee97487f`·`56075b9e`에 있다.
- **상세**: [ADR 0022](../adr/0022-seat-status-relay-and-single-expiration-claim.md)(2026-10-28 채택).

### D2-3. OAuth2 로그인 세션

- **문제**: 로그인 시작(`/api/v1/auth/oauth2/authorize/*`)과 콜백(`/api/v1/auth/oauth2/callback/*`) 사이에 OAuth2
  `state`와 프론트 주소를 HttpSession에 둔다(`OAuth2SecurityConfig`, `OAuth2FrontendRedirectResolver`). 두 요청이 다른
  인스턴스로 가면 `authorization_request_not_found`로 로그인이 실패한다.
- **선택지**:
  - Spring Session Data Redis로 세션을 Redis에 둔다. API 체인은 `STATELESS`라 세션을 만드는 곳이 OAuth2 체인뿐이다.
    의존성과 설정만 늘고 코드는 거의 바뀌지 않는다. Redisson 연결과 함께 쓸 수 있는지 확인이 필요하다.
  - Redis에 state 키를 짧은 TTL로 저장하는 `AuthorizationRequestRepository`를 직접 만들고 프론트 주소 저장도 바꾼다.
    2026-10-17 논의의 기본안이었다. 코드가 수십 줄 늘어난다.
  - state와 프론트 주소를 서명한 쿠키에 담는다. 서버 저장소가 필요 없다.
  - OAuth2 경로에만 LB sticky를 건다. 코드는 그대로지만 LB 설정에 기대게 된다.
- **처음 추천**: Spring Session Data Redis(확인 필요).
- **결정(2026-11-04)**: 로그인 요청 정보를 AES-GCM으로 암호화해 쿠키에 담고, 서버와 Redis에는 저장하지 않는다. 범위는
  "`state` 저장소 교체"가 아니라 "OAuth 로그인의 세션 의존을 전부 없앤다"이다. Spring Security `oauth2Login()`의 `state`
  비교·토큰 교환·예외 처리는 그대로 쓴다.
  1. 암호화 쿠키 `AuthorizationRequestRepository`: JSON(Java 직렬화 금지, 인증 태그 검증 뒤에만 읽음), 쿠키 이름
     `__Host-`(하위 도메인의 cookie tossing 방지, `Path=/`), 이름에 `state` 포함(여러 탭 동시 로그인), 쿠키 안 제공자 이름을
     콜백 제공자와 비교, `HttpOnly`·`Secure`·`SameSite=Lax`, 10분(`Max-Age`와 쿠키 안 발급 시각 둘 다).
  2. FE 주소(`OAuth2FrontendRedirectResolver`)도 같은 쿠키에 담고 `getSession(true)`를 없앤다.
  3. OAuth 체인을 `STATELESS`로 바꾸고 SecurityContext를 세션에 저장하지 않는다. 로그인 전 과정에서 `JSESSIONID`가
     생기지 않는지 테스트로 확인한다(저장소가 세션을 만들면 정책과 무관하게 생긴다).
  4. 기본 `InMemoryOAuth2AuthorizedClientService`가 로그인마다 제공자 토큰을 쌓지 않게 한다(로그인 뒤 쓰지 않는다).
  5. 암호화 키는 환경 변수로 두고 기본값을 두지 않는다. 없으면 기동이 실패한다.
  6. 테스트: 다른 인스턴스에서 읽기, 변조·만료·제공자 불일치 거절, 두 탭 동시 로그인. FE는 바꾸지 않는다.
- **고른 이유**: 로그인 시작은 인증 전 요청이라 누구나 반복할 수 있다. Redis에 저장하면(Spring Session, `state` 키) 그
  데이터가 좌석과 같은 Redis에 쌓이고, `noeviction`(D1-4)이라 메모리가 차면 좌석 선택·선점 쓰기가 실패한다. 쿠키는 각자
  브라우저에만 생겨 서버·Redis 사용량이 늘지 않는다. 운영 재개 전 필수였던 "로그인 시작마다 세션이 무제한 쌓임"
  ([남은 작업](../todo.md))도 함께 사라지고, 서버 대수·ECS와 무관하게 동작한다. Auth0 Next.js SDK와 Auth.js도 로그인
  진행 정보를 암호화 쿠키에 담는다.
- **감수하는 것**: 비밀 키가 하나 는다(바꾸면 그 순간 로그인 중이던 사람만 다시 시작). Spring Security에 공식 쿠키 구현이
  없어(spring-security 이슈 #6549) 저장소를 직접 만들고 테스트한다. 약 1일(추정).
- **고르지 않은 안**:
  - Spring Session Data Redis: Spring 공식 세션 공유 방식이고 코드가 가장 적지만, 인증 전 요청이 좌석 Redis에 쓴다.
    `limit_req`와 짧은 세션 시간은 줄일 뿐 격리하지 못한다(IP가 많은 공격, 한 IP를 여러 사람이 쓰는 환경). 세션 전용 Redis를
    따로 두면 격리되지만 운영할 Redis가 는다.
  - `state`를 Redis 키로 저장: 주소의 `state`가 Redis에 있는지만 보면 로그인을 시작한 브라우저에 묶이지 않아 로그인 CSRF가
    열린다. 묶으려면 쿠키가 더 필요하고 좌석 Redis 문제는 같다.
  - OAuth 경로 sticky(`ip_hash`): 세션 누적이 남고, ECS로 가면 ALB에서 다시 설정해야 한다.
- **범위 밖**: 일회용 로그인 코드를 브라우저에 묶는 것([남은 작업](../todo.md)의 "로그인 CSRF")은 구현 때 함께 할지 정한다.
  리프레시 토큰·일회용 코드와 좌석 Redis의 분리는 D1-5에서 정한다(둘 다 실제 로그인을 끝내야 생겨 인증 전 연타로 쌓이지
  않는다).

### D2-4. SockJS 연결

- **문제**: FE는 `sockjs-client`로 `/ws`에 연결한다. WebSocket으로 연결되면 문제가 없지만, xhr-streaming이나
  polling으로 폴백하면 요청 여러 개가 같은 인스턴스로 가야 한다.
- **선택지**:
  - FE가 `/ws/websocket`으로 순수 WebSocket 연결을 한다. SockJS endpoint는 순수 WebSocket도 받으므로 서버는 그대로다.
  - `/ws/**`에 LB sticky를 건다.
  - 서버에서 SockJS를 걷어낸다(FE도 함께 바꿔야 한다).
- **추천**: FE 순수 WebSocket. 폴백이 꼭 필요한 사용자 환경이 있는지 먼저 확인한다.
- **2026-10-26 제약**: 지금은 FE를 고칠 수 없다. FE 순수 WebSocket과 서버 SockJS 제거는 쓸 수 없으므로, `/ws/**`의 LB
  sticky와 그대로 두기(WebSocket으로 연결되는 사용자는 문제없고 폴백한 사용자만 끊긴다) 중에서 다시 정한다.
- **결정(2026-11-05)**: 그대로 둔다. 서버·nginx·FE 모두 바꾸지 않는다.
- **고른 이유**: 폴백이 필요한 사용자는 방화벽·프록시·백신이 WebSocket을 늘 막는 환경에 있어 다시 시도해도 붙지 않는다.
  그런 환경은 드물고, 끊겨도 잃는 것은 실시간 좌석 갱신뿐이다. 좌석을 고를 수 있는지는 서버가 Redis로 판정하므로(이미
  잡힌 좌석은 409) 잘못 팔리지 않는다. 그래서 sticky 설정을 더해 그 사용자를 붙잡아 둘 만큼의 가치가 없다고 봤다.
- **감수하는 것**: 2대가 되면 폴백으로 붙은 사용자는 요청이 다른 서버로 갈 때마다 끊기고 FE가 5초 뒤 다시 붙는다. 그동안
  좌석 화면은 새로 불러올 때까지 갱신되지 않는다.
- **2대로 늘리기 전 확인**: 운영 nginx가 WebSocket 업그레이드를 넘기는지 본다(브라우저 개발자 도구에서 `/ws/…/websocket`이
  101). 넘기지 않으면 지금 모든 사용자가 폴백이라 2대가 되는 순간 전원이 끊긴다. 그때는 nginx에 업그레이드 헤더를 넣는다.
  ALB(D1-2)는 WebSocket을 그대로 넘기므로 `/ws`가 ALB에서 Core로 바로 가면 이 문제는 사라진다.
- **고르지 않은 안**: `/ws/**` sticky(nginx가 주소의 SockJS 세션 ID로 `hash`): 폴백 사용자도 유지되지만 nginx 설정이
  늘고 ECS로 가면 ALB에서 다시 설정해야 한다. FE 순수 WebSocket이 가장 단순하지만 FE를 고칠 수 없다.
- **다시 볼 것(2026-11-09)**: FE를 고칠 수 있으면 FE 순수 WebSocket + 서버 STOMP 하트비트가 가장 단순하다. FE를 고칠 수
  없고 지금 되는 기능이 깨지면 안 된다는 조건이면 폴백 사용자까지 지키는 sticky가 맞다. FE 개발자에게 묻고 다시
  정한다([FE 변경 요청](fe-change-requests.md) 2). ALB(D1-2)에서는 sticky가 대상 그룹 설정 하나라(`/ws/*`용 대상 그룹을
  따로 두고 쿠키 sticky) nginx `hash`보다 비용이 작다.

### D2-5. FE 재연결 때 좌석 다시 조회

- **문제**: `useSeatSocket`은 연결되면 구독만 하고 좌석 상태를 다시 조회하지 않는다. 연결이 끊긴 동안의 알림과,
  D2-1·D2-2에서 드물게 사라지는 알림을 메울 길이 없다.
- **추천**: 연결·재연결 때 점유 좌석을 다시 조회한다. 스케일 아웃과 상관없이 지금도 필요하다. ticket-fe에서 진행한다.
- **결정(2026-10-26)**: 지금은 하지 않는다. FE를 고칠 수 없다. 그래서 D2-1(구독이 끊긴 동안)과 D2-2(좌석 선택 만료
  claim의 드문 누락, 주문 만료를 꺼낸 뒤 서버가 죽은 경우)에서 "FE 재조회로 메운다"고 한 알림 누락은, 사용자가 화면을
  새로 불러올 때까지 맞춰지지 않는다. 좌석을 실제로 고를 수 있는지는 Redis 키가 정하므로 잘못 팔리지는 않는다.
- **다시 볼 것(2026-11-09)**: FE 개발자에게 묻고 다시 정한다([FE 변경 요청](fe-change-requests.md) 3).

## D3. 중복 실행과 자원(P1)

### D3-1. 스케줄러 중복 실행

- **문제**: 정기 작업이 인스턴스마다 돈다. 같은 대상을 두 대가 함께 처리하거나 같은 알림을 두 번 보내는지 확인해야 한다.
- **선택지**: 모든 인스턴스에서 그대로 둠, `worker.enabled=true`를 한 대에만 둠, ShedLock(DB 테이블과 migration 추가).
- **처음 추천**: `worker.enabled=true`를 한 대에만 둔다. D2-2 뒤로 맞지 않게 됐다(아래 고르지 않은 안).
- **결정(2026-11-09)**: 모든 인스턴스에서 그대로 돌린다. 코드와 설정을 바꾸지 않는다.
- **작업별 확인(2026-11-05, Spring Modulith 2.1.1 소스 포함)**:
  - 주문 만료 청소(`OrderExpirationTrigger`, 5초): 주문 한 건씩 `FOR UPDATE SKIP LOCKED`로 잡아 같은 주문을 두 대가
    처리하지 않는다. 처리 중 죽으면 롤백으로 잠금이 풀려 다른 인스턴스가 다음 순회에서 잡는다.
  - 좌석 선택 만료 알림(`SeatSelectionExpirationTrigger`, 1초): 장부에서 꺼내기와 지우기가 Redis 스크립트 한 번이라 같은
    항목을 두 대가 꺼내지 않는다. 꺼낸 뒤 죽으면 그 알림만 빠진다(선택권은 TTL이 푼다).
  - 실패 이벤트 재처리(`EventPublicationMaintenance.resubmitFailed`, 1분): Modulith가 다시 보내기 전에
    `status != RESUBMITTED` 조건으로 RESUBMITTED를 적고(`JpaEventPublicationRepository`의 `MARK_RESUBMITTED`), 1건이
    바뀐 인스턴스만 보낸다(`DefaultEventPublicationRegistry.processPublications`). 리스너도 Redis 확인으로 멱등이다.
    `withMaxInFlight(4)`는 DB의 RESUBMITTED 개수로 세므로 인스턴스마다가 아니라 전체 4개다.
  - archive 정리(`EventPublicationMaintenance.purgeArchive`, 매일 03시): 같은 삭제를 두 번 해도 결과가 같다.
  - 멈춘 publication을 FAILED로 표시(Modulith staleness, 1분): 같은 갱신을 두 번 해도 결과가 같다.
  - 재시작 때 미완료 publication 재발행(`republish-outstanding-events-on-restart`)은 꺼져 있어 롤링 재시작으로 중복되지
    않는다.
  - 좌석 알림 묶음 전송(`SeatStatusRelay`, 250ms)은 인스턴스마다 자기 WebSocket 구독자에게 보내는 것이라 모든 인스턴스에서
    돌아야 한다. 중복 실행 대상이 아니다.
- **고른 이유**: 막아야 할 중복이 없다. 모든 인스턴스가 돌면 한 대가 내려가도 주문 만료와 선택 만료 알림이 멈추지 않는다.
- **감수하는 것**: 03시 삭제와 staleness 갱신을 인스턴스 수만큼 실행한다(쿼리 몇 개).
- **고르지 않은 안**:
  - `worker.enabled`를 한 대에만: 이 설정은 `SchedulingConfig`째 꺼서 정기 작업 전체가 멈춘다. 그 한 대가 내려가면 주문
    만료(D2-2의 유일한 경로)와 선택 만료 알림도 멈춘다.
  - ShedLock: 의존성과 migration이 늘지만 막을 중복이 없다.
- **함께 볼 것**: 인스턴스가 이벤트 후처리 도중 죽으면 그 publication은 staleness(처리 중 10분) 뒤 FAILED가 되고 최대
  1분 뒤 재처리되어, 주문 종료(`OrderTerminated`) 후처리가 최대 약 11분 늦는다. 인스턴스 수와 무관하지만 롤링 배포마다
  생길 수 있어 graceful shutdown을 D4-1에서 함께 정한다. 주문 생성 후처리는 2026-11-06부터 보관함 없이 커밋 직후 바로
  하므로(`d2074b34`) 해당하지 않는다. 재처리 정체(P0-2)는 [남은 작업](../todo.md)에 있다.

### D3-2. DB 연결 풀 크기

- **정할 것**: 인스턴스당 Hikari 풀 크기와 최대 인스턴스 수.
- **왜**: 전체 연결 수는 (풀 크기 × 인스턴스 수) + seed 작업 + 관측 계정이다. 이 합이 RDS `max_connections` 79 안에
  들어야 한다.
- **처음 추천**: 대당 10을 유지한다. 5대까지 여유가 있다고 봤으나 배포 중 한 대와 seed를 넣지 않은 계산이었다.
- **결정(2026-11-09)**: 대당 10을 유지한다(설정 없이 Hikari 기본값, 시작할 때 10개를 열고 들고 있다). Core는 최대 4대로
  묶는다. ECS로 가서 자동 확장을 쓰면 최대 태스크 수를 4로 건다.
- **연결 예산**: Core 대당 10, 롤링 배포 중 한 대 더(+10), seed 작업(풀 설정이 없어 Spring 기본값이면 최대 10, 확인하지
  않음), psql·RDS 예약분 몇 개. ticket-queue는 datasource가 없어 RDS를 쓰지 않는다. 2대 약 43, 3대 약 53, 4대 약 63,
  5대 약 73이라 예약분을 빼면 5대는 넘을 수 있다.
- **고른 이유**: 운영 03-3(2026-11-09, 1대)에서 60 u/s까지 연결 최대 6개, 70~80 u/s는 10개를 다 쓰고 잠깐 기다렸지만
  PASS였다. 90 u/s FAIL은 호스트 CPU(P-017)가 원인이었고 연결 기다림은 그 결과였다. 2대에서 목표(1대의 1.7배)면 대당
  부하가 70~80 u/s 근처라 10개로 PASS한 구간과 같다.
- **감수하는 것**: 대수 상한 4대. 70~80 u/s 구간의 짧은 연결 기다림.
- **고르지 않은 안**:
  - 대당 늘리기(15~20): RDS가 동시에 처리하는 쿼리 수는 그대로라(메모리 1GB급 추정) 연결만 늘면 RDS 안에서 기다린다.
    79 한도도 2~3대에서 찬다.
  - 대당 줄여 합계를 지금(10)과 같게: RDS는 지금과 같지만 서버마다 기다림이 늘어 2대로 늘린 효과가 준다. RDS가 한계라는
    근거도 없다.
- **확인하지 못한 것**: RDS 자체의 CPU를 측정 기록에 남긴 적이 없다. 2대에서는 RDS가 다음 병목일 수 있어 D3-3에서 같이
  본다. 풀 크기는 수용량 측정 순서대로 한 번에 하나씩만 바꾼다.

### D3-3. 수용량 다시 재기

- **정할 것**: N대 구성에서 잴 조건과 Queue 입장률 R을 다시 계산하는 시점.
- **왜**: 인스턴스 수가 바뀌면 다시 재야 한다([Core 수용량](../core-capacity.md#다시-재야-할-때)). Redis는 모든
  인스턴스가 함께 쓰는 단일 스레드라 대수에 비례해 늘지 않을 수 있다.
- **추천**: D2 전체를 넣고 2대로 늘린 뒤 03-3 사다리로 잰다. R = C × 0.7은 그대로 쓴다.
- **함께 볼 것**: RDS CPU와 Core 연결 기다림을 같이 기록한다(D3-2). 2대에서 1.7배가 안 나오면 RDS부터 의심한다.
- **결정(2026-11-09)**:
  - **언제**: 다음이 끝난 뒤에 잰다. 좌석 알림 묶음 유지 여부([FE 변경 요청](fe-change-requests.md) 1, 되돌리면 처리량이
    크게 준다), Core 전용 호스트 + ALB(D0-3·D1-2), 측정 도구의 서버별 수집(D4-2), Core 호스트 시간 동기화 확인(D4-2).
  - **순서**: 03-3으로 Core 1대(전용 호스트 + ALB) 30초 사다리로 기준선 C1 → 2대 사다리, C2 ≥ C1 × 1.7이면 합격 → 합격하면
    3대 사다리로 확장 곡선 → 운영 구성 2대에서 15분 지속과 대기 20만 명으로 확정(2026-11-04 측정 방식). 단계마다 결과를
    보이고 확인받는다.
  - **1.7배에 못 미치면**: 3대로 가지 않고 멈춰 원인을 찾는다(RDS CPU, 모든 서버가 함께 쓰는 Redis, 앞단·ALB).
  - **같이 기록할 것**: RDS CPU, 서버별 DB 연결 기다림, 서버별 CPU, Redis CPU.
  - **부하 발생기**: 2대 목표는 약 150 u/s 이상이라 한 대(4 vCPU)로 모자랄 수 있다. 1단계에서 발생기 CPU를 보고 모자라면
    분산 실행한다.
  - **Queue 입장률**: 확정한 2대의 C로 R = C × 0.7을 다시 계산해 2대 운영을 시작할 때 반영한다.
- **고른 이유**: 지금 숫자(2026-11-09 첫 FAIL 90 u/s)는 Core가 nginx·FE·Redis와 호스트를 나눠 쓸 때라 2대와 비교할 기준이
  아니다. 15분 지속은 오래 걸려 운영할 구성에서만 한다.
- **감수하는 것**: 3대 측정 동안 Core 호스트 한 대를 몇 시간 더 띄운다(DB 연결 30, D3-2 상한 안).

## D4. 배포와 운영(P2)

### D4-1. 롤링 배포 중 호환 규칙

- **정할 것**: 옛 버전과 새 버전이 함께 도는 동안 지킬 규칙.
- **왜**: 롤링(D1-3)에서는 새 버전이 켜지며 Flyway가 DB를 바꾼 뒤에도 옛 버전이 잠시 요청을 받는다. 두 버전이 같은
  DB·Redis·이벤트 보관함·사용자·비밀값을 함께 쓴다. ECS 롤링·블루/그린도 DB와 Redis는 두 버전이 함께 쓴다.
- **결정(2026-11-09)**:
  1. **원칙**: 새 버전은 바로 전 버전과 같이 돌 수 있어야 한다. 추가(컬럼·표·필드·키)는 그대로 하고, 지우기·이름
     바꾸기·모양 바꾸기는 "추가 → 다음 배포에서 정리"로 나눈다.
  2. **자동 검사**: DB migration만 CI에서 squawk로 검사한다(일반 `CREATE INDEX`, 기본값 없는 NOT NULL, 컬럼 삭제·이름
     변경·타입 변경). 에이전트가 커밋 전에 같은 검사를 돌린다.
  3. **예외**: 나누기가 너무 어렵거나 위험하면 점검 배포(모든 서버를 내렸다 올림, 공지)로 한다. 좌석 판정 Redis 키
     구조 변경이 대표적이다(두 형식을 함께 다루는 Lua가 틀리면 중복 판매).
  4. **종료 설정**: 요청 마무리를 20초(`spring.lifecycle.timeout-per-shutdown-phase`, 기본 30초), 비동기 작업 대기를
     10초(`spring.task.execution.shutdown.await-termination`)로 두고 운영 compose에 `stop_grace_period: 40s`를 둔다. 합
     30초를 Docker 기본 10초가 끊지 않게 하고,
     주문 종료 후처리가 끊겨 약 11분 늦는 것(D3-1)을 막는다. ALB 대상 그룹 대기 시간도 약 40초로 맞추고(D1-2), ECS로
     가면 `stopTimeout`도 같은 기준으로 둔다.
- **원칙을 적용한 예(스킬에 참고로 적는다, 따로 결정하지 않는다)**:
  - DB: 컬럼 삭제는 코드에서 안 쓰는 버전을 먼저 배포하고 다음 배포에서 지운다. 이름 바꾸기는 추가·양쪽 쓰기 → 옛 컬럼
    쓰기 중단 → 삭제(배포 세 번). NOT NULL 추가는 기본값. 새 상태 값은 읽는 버전을 먼저 배포. 데이터가 있는 표의 인덱스는
    `CREATE INDEX CONCURRENTLY`(그 migration은 트랜잭션 밖). `database-change` 스킬과 migration 규칙.
  - Redis·이벤트: 메시지(`seat:status:relay`)와 이벤트 보관함 내용은 필드 추가만 한다(Jackson 3과 Spring Boot 기본값은
    모르는 필드를 무시한다). 새 상태 값은 옛 버전이 메시지를 버리므로 읽는 버전을 먼저 배포한다. 이벤트 클래스 이름과
    리스너 id는 바꾸지 않는다(`BookingEventListenerIdContractTest`). 키에 버전을 붙여 새 키를 쓰는 방식은 두 버전이 서로의
    좌석을 못 봐 중복 판매가 되므로 판정 키에는 쓰지 않는다. `booking-change` 스킬.
  - API·WebSocket: FE가 읽는 계약은 필드 추가만 한다(2026-11-09 좌석 알림 형식 사례). `api-contract-change` 스킬.
  - 비밀값: 모든 서버가 같은 값을 쓰고, 바꿀 때는 옛 키도 받는 기간을 둔다. [운영](../operations.md).
- **고른 이유**: 대부분의 작업은 추가라 신경 쓸 것이 없고, 지우기·이름 바꾸기는 드물다. 원칙 하나와 가장 자주 실수하는
  DB migration의 자동 검사면 충분하다. 에이전트가 코드를 쓰므로 사람 리뷰보다 CI 검사가 확실하고, 에이전트가 실패 메시지를
  보고 고칠 수 있다. 다른 회사도 "직전 버전과 호환"을 원칙으로 두고 DB migration만 도구로 막는 경우가 많다(GitLab 무중단
  migration 가이드, Instacart `strong_migrations`).
- **감수하는 것**: Redis·이벤트·API는 자동 검사가 없어 스킬과 리뷰에 맡긴다. 지우기·이름 바꾸기는 배포가 여러 번이다.
- **고르지 않은 안**:
  - 영역별 규칙 다섯 개를 따로 정하기: 같은 원칙의 반복이라 문서와 결정만 늘었다.
  - 규칙만 두고 자동 검사 없음: 에이전트가 스킬을 놓치면 그대로 통과한다.
  - Redis 키 형식 고정 테스트: 키를 바꿀 일이 드물어 지금은 만들지 않는다.
  - GitLab식 배포 뒤 migration 분리: 이름 바꾸기가 편해지지만 Flyway에 구조를 따로 만들어야 해 과하다.
- **정리한 규칙**: "D2-1·D2-2는 옛 버전과 섞이면 알림이 빠지므로 한 대일 때 배포를 끝낸다"는 2026-10-28 배포로 끝나 지웠다.

### D4-2. 관측과 시계

- **정할 것**: 인스턴스별로 지표를 나눠 볼 태그, 서버 시계 동기화.
- **왜**: 메트릭에는 `service`·`environment`·`version` 태그만 있어 인스턴스를 구분하려면 host나 container 태그가 있어야
  한다. 주문 `expiresAt`은 애플리케이션 서버 시계로 계산하므로 서버끼리 시계가 맞아야 한다.
- **추천**: Datadog이 붙이는 host·container 태그로 나눠 볼 수 있는지 확인하고, EC2 시간 동기화가 켜져 있는지 확인한다.
- **결정(2026-11-09)**:
  1. **서버별 지표**: Core가 붙이는 태그는 그대로 둔다. 호스트마다 뜨는 Datadog 에이전트가 수집한 지표에 `host` 태그를
     붙이므로 그것으로 나눠 본다(ECS는 태스크 태그). 2대가 뜬 뒤 Datadog에서 나뉘는지 확인한다.
  2. **측정 도구**: gatling-test `scripts/capacity/run-step.ps1`은 Core 주소 하나로 `/actuator/prometheus`를 읽는다.
     2대에서는 nginx가 A·B로 번갈아 보내 판정 숫자가 섞이므로, Core 주소를 여러 개 받아 서버마다 읽고 합치게 고친다(요청
     수는 더하고 연결 최대 같은 값은 서버별로 적는다). 부하 발생기가 Core 호스트 포트에 직접 닿게 보안 그룹을 연다.
     D3-3 전에 한다.
  3. **시계**: 좌석 선택·선점 만료는 Lua 안 Redis 시계(`redis.call('TIME')`)라 하나다. 주문 `expiresAt`과 만료 청소·결제
     판단은 서버 시계라 Core 호스트끼리 맞아야 한다(어긋난 만큼 주문이 일찍·늦게 만료되고, 판매 정확성은 Redis가
     지킨다). Core 호스트를 만들 때 `chronyc tracking`으로 Amazon Time Sync 동기화를 확인한다. Amazon Linux는 기본으로
     켜져 있다. ECS Fargate는 AWS가 맞춘다. 코드는 바꾸지 않는다.
- **고르지 않은 안**:
  - Core에 서버 구분 태그를 직접 붙이기: 에이전트 `host` 태그로 충분하다.
  - 측정 판정을 Datadog 지표로 옮기기: Datadog 지표는 10~15초 단위라 1초 수집과 맞지 않고 판정 로직을 다시 짜야 한다.
  - 주문 만료를 DB 시계(`now()`)로 계산하기: 시간 동기화가 켜져 있으면 차이가 작아 코드를 바꿀 이유가 없다.

### E-0. 규모 가정

- **가정(2026-11-13 사용자)**: 초당 수십만 명이 몰리는 오픈이 한 달에 2~3일, 초당 1만 명 단위가 한 달에 10일쯤 있고
  오픈마다 약 30분 이어진다. 피크는 한 달에 약 13회 × 1시간(예열 포함) = 약 13시간이고 나머지는 거의 비어 있다.
- **이 가정에서 나오는 것**:
  - **피크는 대기열이 받는다.** Core 1대(c6i.large)는 초당 약 120~150명이다(2026-11-13 첫 FAIL 130 u/s). 초당 1만 명을
    Core가 직접 받으려면 약 70대, 30만 명이면 약 2,000대이고, 그 전에 DB(RDS 1대)와 Redis가 먼저 막힌다. 그래서 Core는
    대기열이 들여보내는 입장 속도(R = C × 0.7, D3-3)만큼만 받는다. 정할 숫자는 Core 대수가 아니라 입장 속도이고, 그 상한은
    DB 한계로 정해진다. DB 한계는 아직 재지 않았다(지금까지는 Core CPU가 먼저 막혔다).
  - **자동 확장이 아니라 예약 확장.** 지표를 보고 늘리면 수집 1~3분 + 서버 부팅·태스크 시작·JVM 예열이 걸려, 오픈 첫 몇
    분에 몰리는 피크를 놓친다. 오픈 시각은 미리 알므로 15~20분 전에 늘려 두고 끝나면 줄인다(Scheduled Scaling).
  - **오픈에는 Spot을 쓰지 않는다.** 피크 중 회수되면 그대로 장애다.
  - **AWS 계정 vCPU 한도.** 70대면 140 vCPU라 새 계정 기본 한도(EC2·Fargate 각각)를 넘을 수 있다. 기본값은 확인하지 않았다.
  - **Datadog 학생 팩 한도를 넘는다.** 호스트 10대·Fargate 태스크 5개라 이 규모에서는 일부만 골라 감시하거나 유료로 간다.
- **비용(추정, 서울 기억값)**: 초당 1만 명 급(약 70대) 1시간에 EC2 약 7달러, Fargate 약 8달러. 쓴 시간만 내므로 실행
  방식(E-2)에 따른 차이는 작다.

### E-2. 서비스별 실행 방식

- **선택지**: ECS는 태스크 정의·서비스·클러스터가 같고, 태스크를 올릴 컴퓨터를 누가 준비하느냐만 다르다.

  | | Fargate | ECS on EC2 | ECS Managed Instances |
  | --- | --- | --- | --- |
  | 컴퓨터 준비·관리 | AWS(서버가 보이지 않음) | 우리(시작 템플릿·ASG·용량 공급자) | AWS(서버 종류는 지정 가능) |
  | 서버 사양 고정 | 안 됨(CPU 세대 미지정) | 됨(c6i.large) | 됨 |
  | 진단 | 컨테이너 안까지(ECS Exec). 서버 전체 CPU 내역(커널·네트워크 처리·steal)은 안 보임 | 서버 전체(SSH, `top -b -d 1`) | 서버 접속 제한적(추정) |
  | Datadog | 태스크마다 사이드카, 태스크 자원을 나눠 씀. 로그는 FireLens 등 장치가 더 필요 | 서버마다 에이전트(지금과 같음) | 데몬 태스크 지원(Datadog 문서) |
  | 학생 팩 한도 | Fargate 태스크 5개 | 호스트 10대 | 호스트 기준(추정) |
  | 추가 비용 | 없음(단가는 EC2보다 조금 높음) | 없음 | 서버당 관리 수수료(초 단위) |

  학생 팩 한도는 [Datadog 학생 팩](https://studentpack.datadoghq.com/) "Program limits"가 출처다. Datadog 요금 문서는 Fargate
  태스크 수를 5분마다 기록해 달 말에 실행 시간 합으로 청구한다고 하므로, 배포 중 잠깐 넘는 것은 영향이 작을 것으로 본다.
  학생 팩이 이 방식을 그대로 쓰는지, 넘으면 어떻게 되는지는 확인하지 못했다.
- **추천**:

  | 서비스 | 방식 | 이유 |
  | --- | --- | --- |
  | Core | ECS on EC2(c6i.large, 서버 1대에 태스크 1개) | 11월 측정과 같은 사양으로 1·2·3대 곡선을 재고(D0-1), 막히면 서버 전체를 본다 |
  | queue-api | ECS on EC2(Core와 서버를 같이 쓰지 않음) | 1대 처리량을 잰 적이 없어 Core처럼 재야 한다. join은 Redis 왕복이 많아 서버 단위 진단이 필요하다 |
  | FE | Fargate | 잴 대상이 아니다. 관리할 서버가 하나 준다 |
  | queue-scheduler | Fargate(태스크 1~2개 고정) | 회차마다 Redis 락을 잡은 1대만 일해(`RedisQueueAdvancementStore`) 늘려도 빨라지지 않는다 |

  한 클러스터에 EC2와 Fargate 용량 공급자를 함께 붙이고 서비스마다 고른다. ALB도 하나를 같이 쓰고 주소로 나눈다
  (`oneticket.site` → FE·Core, `queue.oneticket.site` → queue-api). nginx는 Core·queue 모두 없어지고 HTTPS는 ALB가 맡는다.
- **감수하는 것**: EC2 쪽은 시작 템플릿·ASG·용량 공급자를 직접 만들고 OS 업데이트를 맡는다(평소 꺼 두고 켤 때 최신 ECS용
  이미지로 만들면 부담이 작다). docker 체크를 다시 켜면 11/10의 15초 멈춤(dockerd·containerd 약 1코어)이 재현될 수 있다(추정,
  E-12).
- **고르지 않은 안**: 전부 Fargate(준비가 가장 적지만 사양 고정과 서버 단위 진단이 안 된다), Managed Instances(측정 조건은
  맞출 수 있지만 관리 수수료가 붙고 서버 접속이 제한적이며 사례가 적다).

### E-6. Redis 위치(queue 포함)

- **queue Redis가 확장의 핵심이다.** queue-api는 상태를 Redis에 두고 토큰은 서명 값이라 대수만 늘리면 된다. 사용자 한
  명은 join·enter를 한 번씩 보내고 `/state`는 Cloudflare가 1~5초 캐시하므로, 서버까지 오는 요청은 거의 전부 Redis Lua로
  간다. Redis 한 대가 받는 join은 초당 수만 단위로 추정하며 잰 적은 없다. 초당 수십만이면 여러 노드로 나눠야 한다.
- **나눌 준비**: queue 키는 `{회차:shard}` hash tag로 128 shard에 나뉘어 있고 Redis Cluster를 고려한 형태다(ticket-queue
  `docs/architecture.md`). ElastiCache 클러스터 모드로 코드 변경 없이 나뉠 가능성이 크다. 회차 단위 키(공개 상태 등)는 한
  노드에 몰리지만 scheduler만 주기적으로 쓴다.
- **Core Redis는 클러스터로 못 간다**(D1-1 CROSSSLOT). 단일 노드 + 복제본이다. Core와 queue Redis는 계속 따로 둔다.
