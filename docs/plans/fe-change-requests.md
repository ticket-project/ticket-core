# FE 변경 요청: 좌석 실시간 알림

- **상태(2026-11-09)**: FE 개발자 확인 대기. 답을 받은 뒤 서버 쪽 방향을 정한다.
- **범위**: ticket-fe의 좌석 화면 실시간 알림(`src/features/booking/lib/seatSocketClient.ts`,
  `src/features/booking/hooks/useSeatSocket.ts`). 세 항목 모두 이 두 파일 안이다.

## 요약

좌석 화면은 서버와 STOMP 연결을 열어 두고, 다른 사람이 좌석을 고르거나 풀면 알림을 받아 좌석 색을 바꾼다. 서버 쪽에서
이 알림을 바꾸거나 바꾸려는 일이 세 가지 있고, 셋 다 FE 수정이 있어야 제대로 된다.

1. **좌석 알림 묶음 형식 읽기(급함)**: 운영 Core는 2026-11-09 07:23부터 알림을 여러 좌석 묶음으로 보낸다. 운영 FE는 옛
   형식만 읽어서 알림을 버린다. 지금 운영 좌석 화면은 실시간으로 갱신되지 않는 것으로 본다.
2. **SockJS를 빼고 WebSocket으로 바로 연결**: 서버를 2대로 늘리면 SockJS 폴백으로 붙은 사용자가 끊긴다.
3. **연결·재연결 때 좌석 다시 조회**: 끊겼던 동안의 알림을 메울 길이 없어 새로고침 전까지 화면이 틀린다.

어느 항목도 판매 정확성과는 무관하다. 좌석을 실제로 잡을 수 있는지는 서버가 Redis로 판정하므로(이미 잡힌 좌석은 409)
같은 좌석이 두 번 팔리지 않는다. 문제는 화면이 늦거나 틀리게 보이는 것이다.

## 1. 좌석 알림 묶음 형식 읽기

- **무엇**: 서버가 250ms 동안 바뀐 좌석을 회차별로 모아 메시지 하나로 보낸다. 같은 좌석은 마지막 상태만 보낸다.
  destination(`/topic/performance/{performanceId}/seats`)은 그대로다.

  ```json
  // 예전: 좌석 하나에 메시지 하나
  {"performanceId": 1, "performanceSeatId": 501, "seatId": 10, "action": "SELECTED", "timestamp": "2026-11-09T07:30:00"}

  // 지금: 회차별 묶음. timestamp 없음, changes 안의 순서는 마지막으로 바뀐 순서
  {"performanceId": 1, "changes": [
    {"performanceSeatId": 501, "seatId": 10, "action": "SELECTED"},
    {"performanceSeatId": 502, "seatId": 11, "action": "RELEASED"}
  ]}
  ```

- **왜 바꿨나**: 알림 하나를 그 회차를 보는 사람 전원에게 하나씩 보내면 메시지 수가 "바뀐 좌석 수 × 보는 사람 수"로
  늘어난다. 묶으면 보는 사람마다 초당 4개로 고정된다. 측정 결과(gatling-test `docs/capacity-log`):
  - 로컬 80 u/s, 30초 동안 서버가 내보낸 메시지 256만 건 → 6.3만 건, 사용자당 Core CPU 97ms → 18ms(2026-11-06).
  - 운영 03-3 첫 FAIL 25 u/s → 90 u/s, 사용자당 Core CPU 55~66ms → 16~17ms(2026-11-09).
- **지금 운영에서 일어나는 일**: 운영 FE(main `e0bbf30`, 2026-05-29 배포)의 `parseSeatEvent`는 메시지 맨 바깥의
  `seatId`를 읽는다. 묶음 메시지에는 맨 바깥 `seatId`가 없어 "좌석 소켓 메시지 파싱 실패"로 버린다. 코드와 배포 기록으로
  판단했고 운영 화면에서는 직접 확인하지 않았다(확인: 좌석 화면 개발자 도구 Console에서 위 경고가 찍히는지).
- **FE에서 바꿀 곳**: `parseSeatEvent`가 `changes`를 읽어 좌석마다 기존 `SeatSelectionEvent`를 만들고,
  `handleSeatEvent`를 좌석마다 부른다. `timestamp`가 없으면 지금처럼 현재 시각을 쓴다.
- **부탁**: 두 형식을 모두 읽게 해 주면 서버와 FE를 어느 순서로 배포해도 안전하다(`changes`가 있으면 묶음, 없으면 예전
  형식).
- **FE를 고칠 수 없으면**: 서버가 모으기·중복 제거는 유지하고 보낼 때만 예전 형식으로 좌석마다 하나씩 보낸다. 운영은
  살아나지만 메시지 수가 묶음 이전에 가까워져 처리량이 25 u/s 근처로 돌아갈 것으로 본다(추정, 재측정 필요).

## 2. SockJS를 빼고 WebSocket으로 바로 연결

- **무엇**: `new SockJS(url)` 대신 `@stomp/stompjs`의 `brokerURL`로 `wss://<API 주소>/ws/websocket`에 바로 연결한다.
  `sockjs-client` 의존성을 지운다. 서버의 `/ws` SockJS endpoint는 `/ws/websocket`으로 오는 순수 WebSocket도 받으므로
  서버 주소는 그대로다.
- **왜**: SockJS는 WebSocket이 막힌 환경에서 HTTP 요청 여러 개로 폴백한다. 폴백 연결 정보는 처음 요청을 받은 서버
  메모리에 있어서, 서버가 2대가 되면 다음 요청이 다른 서버로 갈 때 끊긴다. WebSocket만 쓰면 연결이 하나라 서버 대수와
  무관하고 nginx·ALB에 sticky 설정이 필요 없다.
- **대가**: WebSocket이 늘 막히는 환경(일부 회사·학교 방화벽, 백신)의 사용자는 실시간 갱신을 받지 못한다. 좌석 선택과
  주문은 된다. 이런 환경은 드물다고 본다(확인하지 않음).
- **서버가 먼저 할 것**: STOMP 하트비트를 켠다. 지금은 꺼져 있고(simple broker에 스케줄러 미지정, 기본 `0,0`) SockJS의
  25초 신호가 연결을 살려 두고 있다. SockJS를 빼면 신호가 없어져 좌석 변화가 없는 회차는 nginx·ALB 유휴 시간(기본 60초)마다
  끊긴다. 서버 하트비트(10초)를 켜면 stompjs 기본값(10초)과 맞는다.
- **함께 확인할 것**: 운영 nginx가 WebSocket 업그레이드를 넘기는지(`/ws/…/websocket`이 101). 넘기지 않으면 지금은 전원이
  폴백으로 붙어 있고, SockJS를 빼는 순간 전원이 실시간 갱신을 잃는다.
- **FE를 고칠 수 없으면**: LB가 같은 SockJS 세션의 요청을 같은 서버로 보내게 한다. 스케일 아웃 때 ALB를 들이므로
  (`/ws/*`용 대상 그룹에 쿠키 sticky) 설정 하나로 된다. 지금 결정은 "그대로"(폴백 사용자만 끊김 감수)이며 이 문서의 답을 받은 뒤 다시 정한다
  ([스케일 아웃 결정](scale-out-decisions.md) D2-4).

## 3. 연결·재연결 때 좌석 다시 조회

- **무엇**: `useSeatSocket`의 `onConnect`에서 구독한 뒤, 좌석 화면을 처음 열 때 쓰는 좌석 상태 조회를 다시 부른다(쿼리
  무효화).
- **왜**: 지금은 연결되면 구독만 한다. 연결이 끊겨 재연결(5초)하는 동안 온 알림과, 서버가 드물게 놓치는 알림(좌석 선택
  만료를 장부에서 꺼낸 직후 서버가 죽은 경우 등)을 메울 방법이 없다. 사용자가 새로고침할 때까지 화면이 틀린다.
- **FE를 고칠 수 없으면**: 그대로 둔다. 화면만 틀리고 판매는 틀리지 않는다([스케일 아웃 결정](scale-out-decisions.md) D2-5).

## FE 개발자에게 물을 것

1. 1~3을 고칠 수 있는지, 언제쯤 배포할 수 있는지.
2. 1을 두 형식 모두 읽도록 만들 수 있는지.
3. 운영 FE가 지금 main `e0bbf30`(2026-05-29) 빌드가 맞는지, 그 빌드의 `@stomp/stompjs` 버전.
4. SockJS를 쓴 이유가 따로 있었는지(폴백이 꼭 필요한 사용자 환경이 있었는지).

## 답을 받은 뒤

- 1을 고칠 수 있으면: 서버는 지금 묶음 그대로 두고 FE를 배포한다.
- 1을 고칠 수 없으면: 서버를 예전 형식 전송으로 바꾸고(모으기·중복 제거는 유지) 03-3으로 다시 잰다.
- 2를 고칠 수 있으면: 서버 하트비트를 먼저 배포하고 FE를 배포한 뒤 D2-4를 다시 정한다.
- 3을 고칠 수 있으면: D2-5를 다시 정한다.
