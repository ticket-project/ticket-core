## 이미 확정한 주요 정책

상세 조건과 예외는 반드시 서비스 업무 규칙의 결정 기록·수용 기준을 읽어 확인하라. 아래는 탐색용 요약이다.

- 로그인한 회원만 좌석 선택·주문이 가능하다. 같은 회원·같은 회차의 유효한 결제 대기 주문은 하나만 허용한다.
- 주문 좌석 전체가 본인의 유효한 선택이어야 한다. 하나라도 부적합하면 부분 주문 없이 전체 거절한다.
- 선택은 좌석별 선택 시점부터 5분이다. 추가 선택·반복 요청으로 연장하지 않는다.
- 선점 기간은 회차별 설정이고 주문 기한과 같다. 조회·입력으로 연장하지 않으며 접수 마감으로 기존 기한을 줄이지 않는다.
- 서버 시각이 기한에 도달하면 대기 주문은 만료로 판단한다. DB에 오래된 PENDING이 남았다는 이유만으로 재예매를 막지 않는다.
- 대기 주문 취소는 서버 판정 시 기한 전이면 CANCELED, 기한 도달 이후면 EXPIRED다.
- 본인 CANCELED 반복 취소는 기존 성공으로 응답하고 종료 이력·이벤트를 추가하지 않는다.
  EXPIRED 취소도 정상 응답으로 만료 상태를 알려주며 취소 완료로 안내하지 않는다.
- 주문 화면 새로고침은 서버의 기존 주문을 복원한다. 좌석·저장 금액·상태·남은 시간으로 표시하고 기한을 연장하지 않는다.
- 주문 화면에서 좌석 화면으로 돌아갈 때는 확인 후 기존 주문 종료를 확인한다.
- 주문 탭·브라우저 닫기는 현재의 최선 노력 취소 요청과 원래 기한 만료를 유지한다. 즉시 종료·좌석 해제를 보장하지 않는다.
- 주문 전 선택 화면 새로고침은 현재대로 선택 목록 초기화·해제 시도이며 자동 복원하지 않는다.
- 전체 선택 해제는 같은 회원·같은 회차의 다른 탭도 포함한다. 그 영향을 안내한다.
  예전 해제 요청의 지연·재시도가 그 뒤 생긴 새 선택을 삭제해서는 안 된다.
- 유효한 같은 본인 선택의 재요청은 기존 성공으로 응답한다. 수량·기한·새 성공 이벤트를 추가하지 않는다.
- 만료된 예전 선택 요청의 재도착은 만료 안내이며 자동 재선택하지 않는다.
  사용자가 직접 다시 선택한 새 요청은 당시 조건을 확인하고 성공하면 별도의 5분을 부여한다.
- 회차별 동시 선택·한 주문 수량 상한은 1석 설정도 지원한다. 기존 2석 이상·제한 없음도 유지한다.
- 같은 회원·같은 회차의 총 구매 한도를 별도로 지원한다. 합산 대상은 구매 완료와 기한이 남은 결제 대기다.
  대기에서 완료로 바뀌어도 중복 합산하지 않는다. 취소·만료된 대기는 제외하고 기존 구매 완료 수량은 유지한다.
- 숫자 총 한도 회차는 선택 단계부터 남은 구매 가능 수량과 기존 선택 상한을 모두 적용한다. 주문 생성 시 다시 검사한다.
- 총 구매 한도는 숫자 제한 또는 총 제한 없음이다. 설정을 필수로 두어 예매를 막는 제안은 사용자가 거절했다.
- **가장 최근 결정:** 총 한도를 따로 설정하지 않은 회차의 기본값은 총 제한 없음이다.
  기존 선택·한 주문 수량·유효 주문 수 제한은 계속 적용한다. 정책 조회 실패나 판매 정책 전체 누락은 별개다.

예시의 총 4석·선점 10분 등은 공통 기본값이 아니다. 실제 회차별 숫자는 아직 정하지 않았다.
현재 주문의 결제·구매 확정·PG·발권은 사용자 흐름으로 완성되지 않았다. 상태 모델이 있다는 이유로 구현됐다고 말하지 말라.

## 다음 문답과 남은 일

총 한도의 누락 기본값은 답변을 받아 확정했으므로 다시 질문하지 말라. 다음 정책 질문은 아직 사용자에게 제시하지 않았다.
다음으로 선택 회차의 좌석·가격을 예매 화면의 기준으로 삼을지 확인하는 것을 제안한다.
이는 새 에이전트가 질문할 후보이며 이미 승인된 정책이 아니다.

코드에서 FE 좌석 구성은 공연의 showId를 사용하고, 좌석 상태·선택·주문은 performanceId를 사용한다.
공연 좌석 API는 ID가 가장 작은 회차를 대표로 반환한다. 따라서 회차별 가격·등급·좌석 구성이 다르면 표시와 주문 대상이
달라질 수 있다. 관련 근거는 점검 문서의 ‘선택 회차와 화면의 좌석·가격’에 있다.
관련 소스를 재확인한 뒤 다음처럼 쉬운 예시와 질문 하나로 설명하라.

> 같은 공연이라도 토요일은 5만 원, 일요일은 7만 원일 수 있습니다. 예매 화면의 좌석과 가격은 사용자가 선택한
> 회차를 기준으로 보여주는 것을 권장합니다. 현재 화면은 공연의 대표 회차 정보를 사용해서 다르게 표시될 수 있습니다.
> 선택한 회차의 좌석과 가격을 보여주도록 정할까요?

이후의 우선 검토 후보는 점검 문서를 따르되 한 번에 한 가지씩 다뤄라.

- 주문 화면 새로고침 유지와 현재 pagehide 취소의 충돌, 다중 탭·해제 후 재요청·상태 갱신.

## 문답 진행 방식과 검증

모든 대화·로그·문서는 한국어로 작성하고 파일은 UTF-8 BOM 없이 읽고 써라.
사용자는 ‘유지’, ‘현재’, ‘권장대로’, ‘보완’, ‘어’처럼 짧게 답한다. 직전 질문의 의미를 기준으로 반영하되
답이 모호하면 동의하지 않은 대안까지 확정하지 말라. 특히 ‘아니’를 다른 기본값의 동의로 해석하지 말라.

1. 첫 응답에서 목표·제약·완료 조건을 3줄 이내로 안내한다.
2. 이미 확정된 항목을 다시 묻지 않고 관련 소스·기존 문서를 확인한다.
3. 코드의 현재 동작 → 쉬운 예시 → 권장 규칙과 이유 → 질문 하나 순서로 설명한다.
   사용자가 ‘더 쉽게’를 요청했으므로 기한·상태·요청 식별 같은 개념은 구체적 예시로 풀어라.
4. 답변을 받으면 두 규칙 문서의 결정 기록·수용 기준·관련 규칙·QA 시나리오를 일관되게 갱신한다.
   확정 정책이 코드와 다르면 ‘확정·미적용’과 수정 필요 지점을 기록하고 현재 구현 열을 덮어쓰지 않는다.
5. 문서 변경은 `bash scripts/check-docs.sh`, 변경 링크·앵커·소스 근거 확인, `git diff --check`로 검증한다.
   이 문서 검사 스크립트 자체는 앵커나 외부 링크를 검사하지 않으므로 필요하면 별도로 확인하라.
6. 최근 커밋 형식의 `docs(service): 한국어 설명`과 의미 있는 본문으로 논리적 단위마다 커밋한다.
   작업 전 사용자 변경은 포함하지 않는다. 결과에 실제 검증·커밋과 코드 미적용을 짧게 알린다.
7. 다음 질문 하나를 제시하고 답을 기다린다. 답변 전에 종속 정책을 확정하지 않는다.

Windows에서는 Git Bash의 샌드박스 신호 파이프 제약 때문에 문서 검사 실행에 도구 권한 확장이 필요했던 이력이 있다.
검사가 막히면 환경 제약을 확인하고 승인된 방식으로 실행하라. 실행하지 않은 빌드·서비스 테스트·브라우저 검증을
통과했다고 보고하지 말라. 문서만 변경한 작업에서는 빌드·서비스 테스트를 실행하지 않았다.

이 인계 시점에는 사용자의 요청에 따라 기존 변경과 인계 자료를 커밋·푸시하는 작업을 수행한다.
새 에이전트의 이후 push·PR·배포는 새 요청 범위를 확인하라. 서비스 코드 구현·새 테스트 작성·이슈 생성·다른 에이전트
메시지 전송은 이 정책 문답 작업에 자동으로 포함되지 않는다.
