# 서비스 업무 규칙 — 공동 검토 초안

상태: **공동 검토 중, 아래 결정 기록의 항목만 확정**. 조사 기준일: 2026-10-04.

이 문서는 기획자·개발자·QA가 같은 서비스 동작을 논의하기 위한 출발점이다. 코드를 읽어 확인한 동작을
정리했으며, 그것을 그대로 제품 정책으로 승인한 것은 아니다. 미정 정책, 프로젝트 간 불일치와 수정 후보는
[서비스 규칙 점검 결과](service-rule-review.md)에 있다. 예매의 기술적 구현 기준은 기존
[예매 수명주기](core-booking-lifecycle.md), 용어의 상세 정의는 [용어집](glossary.md)을 따른다.

## 먼저 이해할 것

업무 규칙은 “누가, 어떤 조건에서, 무엇을 할 수 있고, 결과가 어떻게 되는가”를 정하는 문장이다.
예를 들어 “회원은 자신이 선택 중인 좌석으로만 주문을 만들 수 있다”는 업무 규칙이다.
“Redis에 저장한다”는 그 규칙을 구현하는 방법이다. 기획·QA는 업무 규칙을 검토하고, 개발자는 구현 방법을
선택한다. 실패·시간 경계·동시 요청도 사용자에게 결과가 나타나므로 업무 규칙에 포함한다.

| 구분 | 뜻 | 이 문서에서의 취급 |
| --- | --- | --- |
| 현재 구현 | 소스에서 확인한 지금의 동작 | 아래 기능별 표의 기본 상태. 유지 여부는 검토해야 한다 |
| 기존 결정 | ADR·기존 문서에 명시된 결정 | 해당 근거를 연결한다. 문서의 채택·대체·미적용 상태를 확인한다 |
| 결정 필요 | 코드만으로 제품 의도를 정할 수 없는 항목 | 점검 문서의 결정 질문과 연결해 검토한다 |
| 제안 | 앞으로 채택할 수 있는 정책·개선 방향 | 현재 동작이나 확정 정책으로 취급하지 않는다 |
| 예정 기능 | 모델·화면은 있지만 사용자 흐름이 연결되지 않은 기능 | 현재 제공 기능에 포함하지 않는다 |

표의 규칙 ID는 문서·QA 시나리오·추후 테스트를 연결하기 위한 식별자다. GitHub 이슈 번호가 아니다.
규칙 하나를 바꿀 때는 관련 화면·API·설정·테스트를 함께 확인한다.

수용 기준: 비회원의 좌석 선택·주문 생성 요청은 인증 실패로 거절되고 새 선택·주문이 생성되지 않는다.
로그인에 성공했다는 사실만으로 예매가 보장되지는 않으며, 접수 기간·좌석·소유권 등 나머지 조건도 충족해야 한다.
로그아웃·탈퇴·토큰 만료의 효력과 비회원 공개 정보의 상세 범위는 별도 검토한다.

결제 대기 주문 수의 수용 기준: 같은 회원·같은 회차에 유효 기한 안의 PENDING 주문이 있으면 추가 주문을 거절하고,
기존 주문은 유지한다. 다른 회차는 나머지 예매 조건을 충족하면 주문을 생성할 수 있다. 한 주문의 좌석 수는
이 제한과 별개다. 기한이 끝난 주문은 아래 만료·재예매 결정에 따라 중복 제한에서 제외한다. 현재 코드는
DB에 PENDING으로 남아 있는 주문도 중복 검사에 포함하므로 이 부분은 보완해야 한다.

주문 좌석 선택 조건의 수용 기준: 본인이 유효하게 선택 중인 요청 좌석은 나머지 예매 조건도 충족하면 주문할
수 있다. 선택하지 않은 좌석·타인의 선택·만료된 선택을 포함한 요청은 새 주문·선점을 생성하지 않는다.
2석 중 1석만 선택이 유효해도 1석만 부분 주문으로 생성하지 않으며, 다른 회원의 선택·선점은 변경하지 않는다.
선택 해제 후 재선택의 처리와 반복 요청의 응답·복구 방식은 별도 검토한다.

선택 유지 시간의 수용 기준: 14:00에 선택한 A석은 14:05, 14:02에 선택한 B석은 14:07에 각각 만료된다.
B석을 추가하거나 A석의 선택을 재요청해도 A석의 만료 시각은 바뀌지 않는다. 만료 시각에 도달한 선택은
주문 조건을 충족하지 않는다. 주문 생성 후에는 회차별로 설정한 별도의 선점 기간과 주문 만료 기한을 적용한다.
선점 기간의 기본값·실제 회차별 값과 정확한 접수 마감 순간의 허용 여부·판정 단계는 별도 검토한다.

선점 기간 설정 단위의 수용 기준: 선점 기간이 다른 두 회차의 주문은 각각 해당 회차의 설정 기간을 적용한다.
선점과 결제 대기 주문은 동일한 업무 만료 시각을 사용한다. 이 결정은 회차별 설정을 허용한다는 뜻이며,
모든 회차에 특정 분 수를 적용한다는 뜻은 아니다. 선점·주문 기한은 연장하지 않는다.

기한 연장 금지의 수용 기준: 선점 기간이 10분인 회차에서 14:03에 주문을 만들었다면 업무 만료 시각은
14:13이다. 14:10에 주문을 조회하거나 화면에서 입력을 계속해도 만료 시각은 그대로다. 수동·활동 기반
연장 기능은 제공하지 않는다. 예시의 10분은 기본 기간 결정이 아니다. 기한 도달 후 만료 판단·재예매는
아래 결정에 따르며, DB·좌석 정리의 허용 지연과 처리 방식은 별도 검토한다.

만료·재예매의 수용 기준: 결제 대기 주문의 만료 시각이 14:13이라면 서버 시각이 정확히 14:13인 순간부터
그 주문은 만료된 것으로 조회·판정한다. 화면의 남은 초가 0이라는 표시만으로 만료를 판단하지 않는다.
현재 남은 초는 정수이므로 실제 기한까지 1초 미만이 남아 있어도 0으로 표시될 수 있다.

DB에 이전 주문이 PENDING으로 남거나 만료 알림·보완 작업이 지연돼도, 그 주문 자체를 이유로 같은 회원·회차의
새 주문을 거절하지 않는다. 재예매에는 새로 유효한 좌석 선택이 필요하며, 접수 기간·입장 자격·활성 회원·판매 가능
좌석 등 나머지 조건을 다시 확인한다. 같은 좌석을 다시 확보할 수 있다는 보장은 아니다.
뒤늦은 이전 주문의 정리는 새로운 선택·선점이나 다른 회원의 자원을 해제해서는 안 된다.

이 결정은 결제 대기 주문의 기한 판정에 관한 것이다. 이미 취소·확정된 주문을 다시 만료로 바꾸는 규칙은 아니다.
요청 시 정리·조회 시 논리적 판정 등 구현 방식, 실제 DB·좌석 정리의 허용 지연과
향후 결제 승인·만료 경합은 별도 검토한다. 기한 후 취소의 종료 사유는 아래 결정에 따른다.
정책을 기록했으며 서비스 코드는 아직 변경하지 않았다.

접수 마감과 기존 주문 기한의 수용 기준: 접수 마감이 18:00이고 선점 기간이 10분인 회차에서 17:59에
생성한 주문·선점의 기한은 18:09다. 접수 마감 시각인 18:00에 기한을 줄이거나 자동 종료하지 않는다.
회원의 취소 등 별도 종료 사유가 없다면 기존 주문·선점은 자신의 기한까지 유지한다. 예시의 10분은 기본값 결정이 아니다.

접수 마감 후에는 주문 전 좌석 선택이 남아 있더라도 새 주문을 만들 수 없다. 기존 주문을 취소한 뒤 새로 주문하거나,
기존 주문이 만료된 뒤 재예매할 때에도 접수 기간을 다시 확인한다. 이미 생성한 주문의 기한을 보장하는 결정이
새 주문의 접수 기간을 연장하는 뜻은 아니다. 정확히 마감 시각인 순간의 접수 허용 여부와 요청 처리 중 마감을
넘었을 때의 판정 단계는 별도 검토한다. 실제 PG 승인 흐름은 아직 구현되지 않았으므로 이 결정이 현재 결제 기능의
제공을 뜻하지 않는다.

취소·만료 종료 사유의 수용 기준: 만료 시각이 14:13인 결제 대기 주문의 취소를 서버에서 14:12:59에
판정하면 CANCELED, 정확히 14:13이나 그 이후에 판정하면 EXPIRED로 기록한다. 회원의 클릭 시각이나
브라우저 시계가 기준은 아니다. 요청을 기한 전에 보냈어도 서버의 취소 판정이 기한 후라면 EXPIRED다.

기한이 지난 주문이 DB에 PENDING으로 남아 있어도 취소 요청으로 CANCELED를 기록하지 않는다.
이후 만료 작업이 실행돼도 종료 상태·이력·후속 이벤트의 사유가 서로 모순되지 않아야 한다.
기한 전에 이미 CANCELED로 종료한 주문을 기한이 지났다는 이유로 EXPIRED로 바꾸지 않으며,
이미 CONFIRMED인 주문에도 이 규칙을 적용하지 않는다. 종료 처리가 늦어져도 새 선택·선점을 해제하지 않는다.

본인의 이미 취소된 주문에 대한 반복 요청과 만료된 주문의 취소 응답은 아래 결정에 따른다. 확정 주문의 취소 응답과
실제 DB·좌석 정리의 허용 지연은 별도 검토한다. 현재 코드에는 기한 검사 없는 취소 경로가 있으므로
구현 보완 후 위 기준을 검증해야 한다.

반복 취소의 수용 기준: 본인의 주문이 첫 취소로 CANCELED가 됐지만 성공 응답을 받지 못한 경우,
같은 주문에 다시 취소를 요청해도 성공으로 응답한다. 취소 시각은 최초 값으로 유지하고 취소 이력·종료 이벤트를
추가 생성하지 않는다. 취소 요청이 동시에 여러 번 와도 하나의 취소 결과만 남아야 한다.

이미 CANCELED인 주문을 기한 이후에 다시 취소해도 CANCELED를 유지하고 성공으로 응답한다.
반복 요청 때문에 새로 확보된 좌석의 선택·선점을 해제하지 않는다. 최초 종료 이벤트의 전달 실패를 복구하기 위한
재전달은 별도 처리이며, 반복 취소 요청으로 새 종료 이벤트를 만드는 것과 구분한다.
이 결정은 본인의 CANCELED 주문에 한정한다. 소유권 확인을 생략하지 않는다. EXPIRED의 취소 응답은 아래 결정에
따르며, 없는 주문·타인 주문·CONFIRMED 주문의 응답과 주문 생성·좌석 선택의 반복 요청 정책은 별도 검토한다.

만료된 주문의 취소 응답 수용 기준: 본인의 EXPIRED 주문에 취소를 요청하면 정상 응답에 EXPIRED 상태를 전달하고,
화면은 “기한이 지나 만료된 주문입니다”라고 안내한다. 상태를 CANCELED로 바꾸거나 취소 이력을 만들지 않는다.
이미 EXPIRED인 주문의 반복 요청은 기존 만료 시각·종료 이력을 유지하고 새 종료 이벤트를 추가 생성하지 않는다.

만료 기한에 도달했지만 DB에 PENDING으로 남은 주문도 정상 응답으로 EXPIRED를 전달한다. 실제 DB 상태 변경과
종료 이력·이벤트는 만료 처리 기준에 맞춰 수행해야 하며, 반복 요청 때문에 같은 종료를 추가 기록하지 않는다.
정상 응답은 요청 처리 결과를 확인했다는 뜻이며, 화면에 “취소 완료”라고 잘못 표시해서는 안 된다.
소유권 확인은 계속 적용하며, 없는 주문·타인 주문·확정 주문까지 정상 응답 대상으로 확대하지 않는다.
새로 확보된 선택·선점의 소유권은 그대로 보호한다.

현재 취소 API의 성공 본문에는 주문 상태가 없고, FE 취소 함수는 응답 상태를 소비하지 않는다.
구현 시 Core 응답과 FE 안내를 함께 보완하고 기존 API 소비자에 대한 호환성을 확인해야 한다.
구체적인 응답 필드·DB 정리 방식·허용 지연은 이 문답에서 확정하지 않는다.

주문 화면 새로고침의 수용 기준: 결제 대기 주문의 기한이 14:13이고 회원이 14:10에 화면을 새로고침하면,
같은 주문의 좌석·저장된 금액·현재 상태·남은 시간을 서버에서 다시 조회한다. 새로고침 때문에 취소 요청을 보내거나
새 주문·선점을 만들지 않으며, 기한을 14:13 이후로 연장하지 않는다. 접수 마감이 이미 지났어도 유효한 기존 주문의
복원에는 앞서 확정한 기존 기한 유지 정책을 적용한다.

메모리의 선택 목록이 사라지거나 URL·브라우저 저장값이 바뀌어도 해당 값으로 주문 좌석·금액·기한을 확정하지 않는다.
서버의 본인 주문 상세를 기준으로 표시한다. 원래 기한에 도달했다면 만료 상태와 안내를 표시하고 예매를 계속할 수 있는
주문으로 복원하지 않는다. 이미 취소된 주문도 진행 가능한 결제 대기 주문으로 표시하지 않는다.

조회 실패는 취소·만료의 증거가 아니다. 상태를 확인하지 못했음을 표시하고 재조회할 수 있어야 하며,
조회 실패만을 이유로 주문을 자동 취소하거나 새 주문을 생성하지 않는다. 다른 회원의 주문 정보는 복원하지 않는다.
입력 중인 연락처·결제수단·동의 항목의 저장 여부, 로그인 만료 후 복귀 경로, 주문 키를 잃었을 때 주문 찾기,
다른 화면 이동은 별도 검토한다. 주문 전 선택 화면의 새로고침, 주문 화면에서 좌석 선택 화면으로 뒤로가기와
주문 화면의 탭·브라우저 닫기는 아래 결정에 따른다.

주문 화면 뒤로가기의 수용 기준: 유효한 결제 대기 주문에서 좌석 선택 화면으로 돌아가려 하면 기존 주문과
좌석 선점이 종료된다고 안내하고 확인을 받는다. 거절하면 취소 요청 없이 주문 화면에 머물고 기존 기한을 유지한다.
동의하면 본인 주문의 종료를 요청하고 서버에서 종료 결과를 확인한 뒤 좌석 선택 화면으로 이동한다.

서버 판정 시 기한 전이면 CANCELED, 기한에 도달했거나 지났다면 EXPIRED라는 확정 정책을 적용한다.
이미 취소·만료된 주문의 정상 응답도 각각 실제 상태에 맞춰 안내한다. 종료 요청의 실패·응답 유실로 결과가 불명확하면
종료됐다고 단정하지 않으며, 재조회·재시도로 결과를 확인할 수 있어야 한다. 확인 없이 새 주문을 생성하지 않는다.

이전 주문의 좌석을 새 선택으로 자동 전환하거나 같은 좌석의 재확보를 보장하지 않는다. 좌석을 새로 선택하고
새 주문을 만들 때에는 접수 기간·입장 자격·판매 가능 상태 등 나머지 조건을 다시 확인한다. 주문 종료 응답과 실제
좌석 해제 완료는 다를 수 있으므로 화면 이동만으로 즉시 재선택 가능하다고 보장하지 않는다.
이 결정은 좌석 선택 화면으로의 뒤로가기에 한정한다. 탭·브라우저 닫기는 아래 결정에 따르며,
다른 화면 이동은 별도 검토한다.

주문 화면 닫기의 수용 기준: 탭·브라우저를 닫을 때 본인 주문에 백그라운드 취소 요청을 시도한다.
서버가 처리하면 기존 취소·만료 판정 규칙을 적용한다. 요청을 시도했다는 사실만으로 종료 성공을 확정하지 않는다.
요청이 서버에 도달하지 않거나 처리되지 않으면 기존 주문·선점의 원래 기한은 유지하고 기한 만료로 정리한다.
실제 DB·좌석 정리는 지연될 수 있으며, 닫는 순간 좌석 해제가 완료된다는 보장은 하지 않는다.

다시 주문 화면을 열었을 때에는 서버의 실제 상태를 확인한다. 이미 취소·만료됐으면 종료 상태를 안내하고,
아직 기한 안의 결제 대기 주문이면 같은 주문을 복원한다. 닫기나 재방문으로 새 주문을 만들거나 기한을 연장하지 않는다.
취소 성공 후 응답만 유실된 경우에도 새 주문·이력을 임의로 생성하지 않는다.

앞서 확정한 새로고침 유지·복원 정책은 그대로 유효하다. 현재 이탈 코드는 pagehide에서 동일한 취소 경로를
호출하며 새로고침과 닫기를 구분하지 않는다. 두 정책을 구분하는 처리의 설계·구현 가능성과 검증이 필요하며,
현재 코드가 두 정책을 모두 충족한다고 보지 않는다. 구분 방식과 닫기 감지·취소 전달의 성공 보장은 확정하지 않는다.
같은 주문을 여러 탭에서 열었을 때의 닫기 적용 범위, 주문 전 선택 단계의 닫기와 다른 화면 이동은 별도 검토한다.

선택 화면 새로고침의 수용 기준: 주문을 만들기 전에 좌석을 선택하고 새로고침하면 화면의 선택 목록을 초기화한다.
기존 서버 선택의 해제를 시도하고, 선택 목록을 자동 복원하거나 같은 좌석을 자동 재선택하지 않는다.
주문·선점을 생성하거나 기존 선택 기한을 연장하지 않는다. 다시 선택할 때는 현재 판매·점유 상태와 예매 조건을 확인하며,
이전 좌석의 재확보를 보장하지 않는다.

화면 초기화와 서버 해제 성공은 별개다. 해제 요청이 전달되지 않거나 처리되지 않으면 서버 선택은 원래 좌석별
5분 기한까지 남을 수 있다. 화면이 비었다는 이유만으로 좌석이 해제됐다고 단정하지 않으며, 서버 현황을 기준으로
다시 선택 가능 여부를 판단한다. 다른 회원의 선택·선점은 해제하지 않는다.

이 정책은 주문 화면 새로고침의 유지·복원 결정과 구분한다. 현재 전체 선택 해제는 회원·회차 단위이므로 다른 탭의
선택에도 영향을 줄 수 있다. 다중 탭에서의 적용 범위·안내, 늦게 도착한 해제 요청이 새 선택에 미치는 영향의 방어,
해제 실패 후 재시도·복구 경로와 선택 화면의 닫기·다른 화면 이동은 추가 검토한다.

## 제공 범위와 사용자

브라우저 탭마다 독립된 자원이 아니다. ADMIN 역할 값은 존재하지만 역할별 운영 업무는 별도 정의가 필요하다.

## 좌석 선택·현황

| ID | 조건·행동 | 현재 결과 | 결정할 사항 |
| --- | --- | --- | --- |
| B-01 | 회차 좌석 현황을 조회한다 | 판매 불가 상태, 다른 사람 또는 본인의 선택, 선점이 있으면 OCCUPIED다 | 본인 선택을 별도 표시·복원할 응답 |
| B-02 | 잔여석 수를 조회한다 | 판매 가능 좌석 중 선택·선점되지 않은 좌석을 등급별로 센다 | 조회값은 참고이며 최종 확보는 선택·주문 결과로 판단 |
| B-03 | 좌석을 선택한다 | 해당 회차에서 판매 가능한 실제 좌석이어야 한다. 선택·선점 충돌과 회원별 선택 수를 검사한다 | 예매 화면과 서버의 같은 수량 기준 |
| B-04 | 선택에 성공한다 | 좌석별로 5분 동안 선택을 유지한다 | 좌석마다 시작 시각이 다른 정책 / 세션 전체 동일 기한 |
| B-05 | 본인이 선택한 좌석을 다시 선택한다 | 이미 선택됐다는 충돌을 반환하며 선택 시간을 연장하지 않는다 | 응답 유실 후 재시도는 기존 성공으로 반환할지 |
| B-06 | 선택을 해제한다 | 본인 좌석만 해제한다. 이미 선택이 없으면 성공하고, 다른 회원 소유면 거절한다 | 현재 동작 유지 여부 |
| B-07 | 전체 선택을 해제한다 | 해당 회원·회차의 선택을 함께 해제한다 | 다른 탭에서 선택한 좌석도 함께 해제됨을 안내할지 |
| B-08 | 선택이 만료된다 | 해당 선택은 더 이상 주문에 사용할 수 없다. 최근 만료 기록으로 재선택 안내 오류를 구분한다 | 선택 만료 메시지와 화면 갱신 |
| B-09 | 주문 생성으로 선점이 생긴다 | 후속 처리에서 해당 회원의 선택을 정리하고 선점 상태를 알린다 | 화면 반영 지연·재조회 기준 |
| B-10 | 실시간 좌석 변경을 수신한다 | 선택·해제·선점·해제 이벤트를 반영한다. 알림 수신이 좌석 확보를 보장하지 않는다 | 누락·역순·재연결 때 서버 현황 재조회 |
| B-11 | 좌석 수 상한을 설정한다 | 제한 없음 또는 2 이상만 설정 가능하다. 이는 한 번의 주문 요청 수와 동시 선택 수에 적용된다 | 1석 제한 지원, 회원의 누적 구매 한도와 구분 |

| Queue 순서 구간 | 기본 50ms 구간, 128개 분할, 종료 유예 200ms | 기술 기본값과 사용자에게 약속할 공정성 규칙을 구분한다 |
| 접근·갱신 토큰 기간 | Core 환경 변수에서 주입 | 프로젝트 코드만으로 운영 기간을 확정할 수 없다 |

근거: [Core Clock](../src/main/java/com/ticket/shared/config/SystemClockConfig.java),
[Core 설정](../src/main/resources/application.yml),
[Queue 기본 설정](../../ticket-queue/src/main/java/com/ticket/queue/config/QueueProperties.java).

## 규칙을 테스트로 옮기는 순서

먼저 규칙의 결정 질문을 해결한다. 그다음 사람이 읽는 수용 기준을 만들고, 그 기준을 어디서 검사할지 선택한다.
현재 코드의 결과만 따라 테스트를 늘리면 의도하지 않은 동작도 고정할 수 있다.

| 규칙 예 | 사람이 먼저 합의할 수용 기준 예 | 이후 개발자가 선택할 검사 |
| --- | --- | --- |
| 본인 선택 필수 O-01 | A가 선택한 좌석으로 B가 주문하면 거절되고, A의 선택은 유지된다 | 업무 로직 검사 + 실제 저장소·동시 요청 검사 |
| 주문 전체 성공 O-04 | 2석 중 1석이 이미 선점됐다면 새 주문은 없고 나머지 1석도 새 선점으로 남지 않는다 | 실패 보상·Redis 통합 검사 |
| 접수 경계 E-01 | 마감이 18:00일 때 정확히 18:00 요청을 허용할지 먼저 결정한다 | 고정 시각으로 경계 검사 + 요청 중 마감 검사 |
| 금액 O-05~07 | 선택 회차의 화면 금액과 서버 주문 금액이 같고 요청값으로 가격을 바꿀 수 없다 | API 계약·다른 회차 데이터·화면 흐름 검사 |
| 주문 화면 새로고침 O-17 | 기존 주문을 유지하고 서버의 좌석·금액·상태·기한으로 복원한다. 기한은 연장하지 않는다. 조회 실패 때도 주문을 임의 취소·재생성하지 않는다 | 브라우저 흐름·응답 유실·복구 검사 |

전체 초기 시나리오는 [점검 결과의 QA 검토 시나리오](service-rule-review.md#qa-검토-시나리오)에 있다.
테스트 도구·실행 기준은 [테스트 기준](testing.md)을 따른다.

### 규칙 확정 기록 양식

```text
규칙 ID / 제목:
현재 동작과 근거:
확정할 문장: 누가 / 조건 / 행동 / 성공 결과 / 실패 결과
시간·수량·금액의 경계:
반복 요청·동시 요청·통신 실패의 결과:
합의한 예시와 반례:
화면·API·데이터 변경 범위:
결정일 / 검토 참여자 / 적용 상태:
연결된 이슈 / 수용 기준 / 테스트:
```

담당자·승인자·기간은 이 초안에서 임의로 지정하지 않는다. 기획은 허용·거절 및 고객 안내를, 개발은 구현
가능성과 장애·경합 결과를, QA는 예시·경계·재현 조건을 함께 검토한다. 결정 후 이 문서에 확정 문장과 근거를
기록하고 변경 필요 항목은 저장소의 GitHub Issues 절차로 추적한다.
