# 캐시 옵션 한 줄이 서버를 3분 멈췄다: 운영 부하 테스트에서 찾은 연결 풀 데드락

- 판매 정책을 1초 캐시하자 운영 서버가 **초당 50명**까지 버텼다. 그런데 초당 60명에서는 CPU가 오히려 떨어지며 서버가 멈췄고, 부하가 끝난 뒤에도 **3분 30초** 동안 응답하지 않았다.
- 원인은 `@Cacheable(sync = true)`였다. DB 연결을 쥔 요청은 캐시가 채워지기를 기다리고, 캐시를 채우는 요청은 연결을 기다렸다. 서로를 기다리는 **연결 풀 데드락**이었다.
- `sync = true`를 지우자 멈춤은 사라졌다. 초당 60명은 여전히 실패했지만, 이번에는 CPU가 끝까지 일하다 밀리는 정직한 실패였다.

## 무엇을 쟀나

공연 티켓 예매 백엔드(Spring Boot, JPA, PostgreSQL, Redis)다. 코드는 [ticket-core](https://github.com/ticket-project/ticket-core), 부하 테스트는 [gatling-test](https://github.com/ticket-project/gatling-test)에 있다.
이번에는 PC가 아니라 운영 환경에서 쟀다.

| 항목 | 값 |
| --- | --- |
| 서버 | EC2 한 대(2 vCPU, 메모리 1.9GB). 같은 호스트에 Redis·nginx·Datadog Agent |
| DB | RDS PostgreSQL(최대 연결 79) |
| 연결 풀·요청 스레드 | HikariCP 10개(연결 대기 시간 초과 30초), Tomcat 200개 |
| 데이터 | 회원 100만 명, 과거 주문 약 500만 건, 15,000석짜리 회차 |
| 부하 | 같은 리전의 다른 EC2에서 Gatling으로 초당 N명을 30초 동안 넣는다 |

가상 사용자 한 명은 점유 좌석 조회 → 좌석 선택 → 주문 생성을 한다. 서버 밖으로 새는 기술 실패가 0.1% 이상이거나, 요청 응답이 기준(조회 p99 1초, 쓰기 p99 2초)을 넘거나, 주입이 끝났을 때 서버 안에 남은 사용자가 1초 분량보다 많으면 실패로 봤다.

## 1. 판매 정책을 1초 캐시했더니 초당 50명까지 올랐다

지난 운영 측정의 한계는 호스트 CPU였다. 초당 50명에서 2 vCPU가 다 찼다. 사용자 한 명은 좌석 조회·선택·주문마다 진입 검사를 받으면서 같은 판매 정책 행을 DB에서 세 번 읽고 있었다.
판매 정책은 판매 중에 거의 바뀌지 않는다. 그래서 회차별로 1초 동안 서버 메모리(Caffeine)에 두고 재사용했다.

```java
@Cacheable(cacheNames = CacheNames.SALES_POLICY, key = "#performanceId", sync = true)
public PerformanceSalesPolicy requirePolicy(final Long performanceId) {
    return performanceSalesPolicyRepository
            .findById(performanceId)
            .orElseThrow(() -> new PerformanceSalesPolicyNotFoundException(performanceId));
}
```

`sync = true`는 만료 순간 같은 회차 요청이 한꺼번에 DB로 몰리지 않도록, 한 요청만 읽고 나머지는 그 결과를 기다리게 하는 옵션이다. 실제로 판매 정책 DB 읽기는 30초 측정마다 30번, 1초에 1번이었다.

같은 기간에 사용자 흐름의 요청 수도 5개에서 3개로 줄였으므로, 아래 차이는 요청 줄이기와 캐시를 합친 결과다.

| 초당 50명 | 지난 측정 | 이번(요청 줄이기 + 캐시) |
| --- | --- | --- |
| 판정 | FAIL | **PASS** |
| 사용자당 DB 연결 빌림 | 10번 | 6번 |
| 사용자당 저장소 호출 | 20번 | 8번 |

배운 점: 거의 바뀌지 않는 값을 요청마다 읽고 있다면 짧은 캐시만으로도 한 단계 오른다.

## 2. 초당 60명: CPU가 떨어지면서 서버가 멈췄다

초당 60명에서는 세 번 모두 크게 무너졌다.

| 초당 60명 | 성공 / 시작 | 체류 p95 | 주입 끝에 서버 안에 남은 사용자 | 기술 실패 |
| --- | --- | --- | --- | --- |
| 1회 | 1,787 / 1,800 | 38.6초 | 851명 | 0.72% |
| 재현 | 1,329 / 1,800 | 40.8초 | 1,458명 | 26.2% |
| 진단 | 479 / 1,800 | - | - | 73.4% |

이상한 것은 무너지는 모양이었다. 지난번 CPU 포화 때는 CPU가 1.0에 붙은 채 점점 느려졌다. 이번에는 연결 풀이 다 차고 요청 스레드가 쌓이는 순간 **CPU가 떨어졌다**. 1초마다 모은 지표의 일부다.

14:23:18  10        60        42              0.80     1.00
14:23:20  10        36        101             0.25     0.30
14:23:21  10        36        163             0.10     0.18
14:23:22  (지표 수집 요청도 시간 초과)

세 번째 실행이 끝난 뒤에는 부하가 없는데도 API가 20초 안에 답하지 않았다. Datadog에서 보니 컨테이너는 재시작 없이 살아 있었고 CPU는 0.03코어였다. 멈췄는데 CPU를 쓰지 않는다면, 무언가를 기다리고 있다는 뜻이다.

## 3. 30초의 배수와 210초

Datadog APM에서 60초 넘게 걸린 요청을 모았다. 14:26 무렵 시작한 요청들이 180~212초 동안 붙잡혀 있다가 14:29:38에 **한꺼번에** 끝났다. 500으로 끝난 요청은 끝난 시각이 시작 뒤 60·90·120·150초였다.

```text
14:26:08 → 14:29:38  210.0s  POST /api/v1/orders              201
14:26:08 → 14:27:08   60.0s  POST .../seats/{seatId}/select    500
14:26:08 → 14:27:38   90.0s  POST .../seats/{seatId}/select    500
14:26:38 → 14:28:38  120.0s  GET  .../seats/occupied           500
```

30초는 HikariCP가 연결을 기다리다 포기하는 시간이다. 연결 대기 시간 초과가 한 번 이상 일어났다는 뜻이다.

210초 걸린 주문 trace를 열자 **첫 210초 동안 하위 span이 하나도 없었다**. 첫 DB 조회가 +210초에야 시작했고, 그 뒤의 DB·Redis 호출은 1초 안에 끝났다.

<!-- 그림 2: Datadog 210초 주문 trace의 flame graph(앞 210초가 비어 있음) -->

처음에는 연결을 기다렸다고 생각했다. 하지만 연결 대기는 30초를 넘으면 예외로 끝난다. 한 번에 210초를 기다릴 수는 없다. 그렇다면 첫 DB 호출 앞에 있는 다른 무언가를 기다렸다. 주문 흐름에서 그 앞에 있는 것은 트랜잭션 시작과 판매 정책 조회뿐이고, 판매 정책은 캐시에 적중하면 span을 남기지 않는다.

배운 점: 시간 초과 값은 단서다. 그리고 그 값을 넘는 대기는 다른 곳을 가리킨다.

## 4. 캐시를 채우는 쪽이 연결을 기다리고 있었다

오류 span을 resource별로 세자 판매 정책 캐시를 채우는 DB 호출이 나왔다.

```text
resource: PerformanceSalesPolicyRepository.findById   status: error
count: 9   duration: 30.0 ~ 30.3s
error.message: Could not open JPA EntityManager for transaction
```

9번 모두 연결을 30초 동안 얻지 못해 실패했다. 서버가 멈춘 3분 30초 동안에는 30초마다 한 번씩 7번 연속으로 실패했고, 적재가 한 번 성공하자 모든 요청이 풀렸다. 연결 하나를 얻는 데 기다린 평균 시간도 초당 50명 11.6ms에서 초당 60명 485.6ms로 뛰었다.

`requirePolicy`를 부르는 곳을 따라가자, 트랜잭션 안과 밖의 호출이 같은 캐시를 함께 쓰고 있었다.

```java
// 주문 생성 사전 확인: 트랜잭션을 시작하며 연결을 잡고, 그 안에서 캐시를 부른다
@Transactional(readOnly = true)
public Preflight read(/* ... */) {
    final PerformanceSalesPolicy policy = bookingEntryGuard.check(performanceId, memberId, admissionToken, now);
    // ...
}

// 점유 좌석 조회·좌석 선택: 트랜잭션 없이 같은 캐시를 부른다
public Output execute(final Input input) {
    bookingEntryGuard.check(performanceId, input.memberId(), input.admissionToken(), LocalDateTime.now(clock));
    // ...
}
```

`sync = true`는 Caffeine 내부에서 `ConcurrentHashMap.compute`로 동작한다. 같은 키를 누군가 채우는 동안 나머지는 그 키의 잠금 앞에서 기다린다. 그리고 채우는 일(원래 메서드 본문)은 **그 순간 채우기를 맡은 요청의 스레드에서, 그 요청의 트랜잭션 상태로** 실행된다. 이것을 합치면 고리가 된다.

1. 판매 정책 캐시가 만료된다(1초마다).
2. 트랜잭션 밖의 좌석 선택 요청 X가 먼저 와서 채우기를 맡는다. `findById`가 새 트랜잭션을 열려고 연결을 기다린다.
3. 주문 요청 10개가 각자 연결을 잡은 채 판매 정책을 달라고 한다. X가 채우는 중이므로 연결을 쥔 채 기다린다.
4. 연결 10개가 모두 기다리는 쪽에 있어 X는 연결을 얻지 못하고, 30초 뒤 실패한다.
5. 다음으로 채우기를 맡은 요청도 트랜잭션 밖 요청이면 4가 되풀이된다.

<!-- 그림 3: 위 고리를 그린 그림(주문 요청 10개 ↔ 연결 풀 10 ↔ 캐시를 채우는 요청) -->

데드락의 네 조건(한 번에 하나만 씀, 쥔 채로 기다림, 빼앗을 수 없음, 서로 기다림)이 모두 맞는다. HikariCP의 30초 시간 초과가 고리를 잠깐씩 끊어 줘서 영원히 멈추지는 않았을 뿐이다. 초당 50명에서는 연결 10개가 모두 차는 순간이 짧아(대기 최대 41명이 2초 안에 빠졌다) 고리가 닫히지 않았다.

이 데드락은 DB도 JVM도 알려 주지 않는다. PostgreSQL 잠금끼리 엉킨 것이 아니라 DB의 데드락 감지기에 걸리지 않고, JVM의 데드락 감지는 모니터 잠금 사이의 고리만 찾는다. "연결 풀에 빈자리가 나기를 기다리는 것"은 잠금으로 보지 않는다.

틀렸던 가설은 두 개다. 하나는 "지난번처럼 CPU 포화다"였다. CPU 포화는 연결 풀을 처음 채운 방아쇠였을 뿐, 몇 분씩 멈추게 하지는 못한다. 다른 하나는 "210초 동안 연결을 기다렸다"였다. 이 모순이 캐시를 의심하게 만들었다.

배운 점: 여러 요청이 함께 기다리는 지점(`sync` 캐시, `synchronized`, `compute`, 분산 락)에서, 기다리는 쪽이 쥔 자원을 채우는 쪽이 필요로 하면 데드락이 생긴다.

## 5. `sync = true` 한 줄을 지웠다

선택지를 견줘 봤다.

| 방안 | 판단 |
| --- | --- |
| `sync = true` 빼기 | 한 줄이다. 아무도 다른 요청을 기다리지 않으므로 호출 위치와 상관없이 안전하다 |
| 주문에서 캐시 조회를 트랜잭션 앞으로 옮기기 | 맞는 방향이지만, 트랜잭션 안에서 같은 캐시를 부르는 곳이 두 군데 더 남는다 |
| `refreshAfterWrite`로 옛 값을 주고 뒤에서 갱신 | 설정성 데이터의 정석이지만 `@Cacheable`만으로는 안 되고 구조가 커진다 |
| 만료 시간 늘리기, 연결 대기 시간 줄이기 | 빈도나 멈추는 시간만 준다 |
| 연결 풀 키우기 | HikariCP 위키의 pool-locking 계산(`스레드 수 × (동시에 쥐는 연결 수 − 1) + 1`)으로 201개가 필요한데, DB 최대 연결이 79다 |

```diff
- @Cacheable(cacheNames = CacheNames.SALES_POLICY, key = "#performanceId", sync = true)
+ @Cacheable(cacheNames = CacheNames.SALES_POLICY, key = "#performanceId")
  public PerformanceSalesPolicy requirePolicy(final Long performanceId) {
```

`sync`가 없으면 Spring은 "꺼내 보기 → 없으면 메서드 실행 → 넣기"를 잠금 없이 한다. 트랜잭션 안의 요청은 캐시를 놓치면 이미 쥔 연결로 바로 읽는다. 트랜잭션 밖의 요청은 연결을 빌려 읽지만, 그 요청을 기다리는 다른 요청이 없다.

배포한 뒤 같은 데이터로 초당 60명을 다시 세 번 쟀다.

| 초당 60명 | 고치기 전 | 고친 뒤 |
| --- | --- | --- |
| 연결 풀이 찼을 때 서버 CPU | 0.1~0.3으로 떨어짐 | 0.8~0.95 유지 |
| 부하가 끝난 뒤 회복 | 최대 3분 30초 | 20~40초 |
| 캐시 적재 실패 | 9번(모두 30초) | 0번 |
| 판매 정책 DB 읽기(30초당) | 30번 | 129~203번 |
| 판정 | FAIL(멈춤) | FAIL(CPU 포화) |

멈춤은 사라졌다. 대가로 판매 정책 DB 읽기가 늘었다. 1초에 한두 번 늘 것으로 예상했지만 실제로는 초당 4~7번이었다. CPU가 꽉 찬 상태에서는 한 번 읽는 시간이 길어져, 그사이 캐시를 놓치는 요청이 많아진다. 연결 빌림 전체의 1~2%라 한계에 주는 영향은 작다고 보고 있다.

초당 60명이 여전히 실패한 것은 CPU 포화 때문이다. 다만 이번 재측정은 배포 직후 서버를 짧게 예열하고 바로 초당 60명으로 쟀다. 사용자당 CPU가 실행마다 56.6 → 50.0 → 45.5ms로 줄었으니 JIT 예열이 덜 된 몫이 섞여 있다고 본다.

아직 확인하지 못한 것도 있다. 운영 이미지에 `jcmd`가 없어 스레드 덤프로 고리를 직접 보지 못했다. 다음에 멈추면 덤프에서 주문 사전 확인 아래 `ConcurrentHashMap.compute`에 `BLOCKED`된 스레드들과 `HikariPool.getConnection`에서 기다리는 스레드 하나를 찾으면 확정할 수 있다. 연결 풀을 2개로 줄여 데드락을 재현하는 동시성 테스트도 아직 만들지 않았다.

배운 점: 트랜잭션 안에서는 DB 일만 한다. 우리 문서에는 "예매 정책 조회는 트랜잭션 밖에서 끝낸다"는 규칙이 이미 있었는데 코드가 어기고 있었다. 캐시가 없을 때는 쿼리가 한 번 더 나갈 뿐이라 드러나지 않았고, 캐시가 기다림을 들여오자 문제가 됐다.

## 6. 덤: 실패를 낸 것은 nginx였다

고친 뒤 첫 실행의 기술 실패 10.4%는 서버가 아니라 nginx에서 났다. 서버 안에 1,000명 넘게 밀리자 nginx 로그에 이런 줄이 쏟아졌다.

```text
[crit] accept4() failed (24: No file descriptors available)
[alert] socket() failed (24: No file descriptors available) while connecting to upstream
"POST /api/v1/performances/.../seats/.../select HTTP/1.1" 500
```

nginx 워커 하나가 열 수 있는 파일이 1,024개였고 `worker_rlimit_nofile` 설정이 없었다. 프록시 요청 하나가 클라이언트와 upstream 연결로 파일 디스크립터 두 개를 쓰니, 워커 두 개로 약 1,000개 요청이 한계다. 서버가 이미 밀린 뒤에 생기는 문제지만, 실패 원인을 서버 쪽에서 찾게 만든다.

배운 점: 실패가 어디서 났는지는 서버 trace만 보지 말고 앞단 로그와 함께 센다.

## 정리

| 단계 | 결과 |
| --- | --- |
| 판매 정책 1초 캐시(`sync = true`) | 초당 50명 통과, 60명에서 서버가 최대 3분 30초 멈춤 |
| `sync = true` 제거 | 멈춤 없음, 60명은 CPU 포화로 실패. 한계는 초당 50~60명 사이 |

배운 점 세 가지:

1. 멈췄는데 CPU를 쓰지 않으면 기다림이다. 연결 대기가 늘 때 CPU가 떨어지는 조합은 경보를 걸어 둘 만하다.
2. 함께 기다리는 지점을 만들 때는 "기다리는 쪽이 부족한 자원을 쥐고 있나, 채우는 쪽이 그 자원을 새로 얻어야 하나"를 확인한다. 둘 다 그렇다면 고리가 생긴다.
3. 규칙은 문서보다 코드로 막는다. 진입 검사를 부르는 bean에 `@Transactional(propagation = Propagation.NEVER)`를 붙이면, 트랜잭션 안에서 부르는 순간 테스트가 실패한다. 측정 환경에서 HikariCP `leakDetectionThreshold`를 켜면 연결을 오래 쥔 위치가 로그에 남아, 덤프 없이도 단서를 얻는다.

다음에는 같은 기동에서 낮은 부하부터 충분히 데운 뒤 초당 50명과 55명을 재서 한계를 정할 생각이다. CPU를 더 줄일지, 서버 사양을 올릴지는 그 숫자를 보고 정한다.
