# 병목 하나를 걷어내면 다음 병목이 보였다: 티켓 예매 부하 테스트 하루

- 주문 500만 건이 쌓인 환경에서 예매 흐름에 부하를 걸었더니 **초당 10명**에서 무너졌다(p99 14.7초).
- 인덱스, 필요한 열만 읽기, 응답 압축으로 서버 쪽 병목을 걷어냈다. 중간에 로컬 Docker 포트 중계와 부하 도구의 파일 쓰기라는 측정 환경 문제도 찾아 고쳤다.
- 결과: 측정한 최대치인 **초당 100명**을 사용자 p99 0.2~0.3초로 통과했다.

## 무엇을 쟀나

공연 티켓 예매 백엔드(Spring Boot, PostgreSQL, Redis)다. 코드는 [ticket-core](https://github.com/ticket-project/ticket-core), 부하 테스트는 [gatling-test](https://github.com/ticket-project/gatling-test)에 있다.
가상 사용자 한 명은 공연 요약 → 좌석 상태 → 좌석 선택 → 주문 생성 → 주문 상태를 한 번씩 부른다.

데이터는 회원 100만 명, 과거 주문 500만 건, 좌석 15,000석짜리 회차다. 같은 PC의 Gatling으로 초당 사용자 수를 5명에서 100명까지 올리며 30초씩 쟀다.
사용자 한 명이 다섯 요청을 끝내는 시간의 p99가 5초를 넘으면 실패로 봤다.

## 1. 주문할 때마다 주문 500만 건을 다 읽었다

초당 10명에서 p99가 14.7초까지 늘었다. 주문을 만들기 전에 "이 회원이 이 회차에 진행 중인 주문이 있나"를 확인하는데, 이 쿼리가 인덱스 없이 매번 주문 500만 건을 훑고 있었다.

진행 중(PENDING) 주문만 담는 **부분 인덱스**를 넣었다. 전화번호부 전체 대신 "아직 결제 안 한 주문"만 적은 작은 수첩을 따로 두는 셈이다. 진행 중 주문은 몇 분 안에 결제되거나 만료되므로 이 수첩은 늘 작다.

```sql
CREATE INDEX idx_orders_pending_member_performance
    ON orders (member_id, performance_id)
    WHERE status = 'PENDING';
```

| 초당 10명 | 전 | 후 |
| --- | --- | --- |
| 사용자 p99 | 14,688ms | **114ms** |
| 진행 중 주문 확인 쿼리 평균 | 922ms | 0.6ms |

부하 없이 같은 쿼리의 실행 계획만 보면, 인덱스 없이는 약 500만 행을 읽고 버리며 177ms, 부분 인덱스로는 0.05ms였다. 부하 중에는 여러 요청이 동시에 주문 전체를 읽느라 평균 922ms까지 늘었다.

배운 점: "있는지만 확인하는" 가벼워 보이는 쿼리도 데이터가 커지면 전체를 읽는다.

## 2. 다섯 API가 한꺼번에 느려졌다

이번에는 초당 40명에서 다섯 API가 모두 함께 느려졌다. DB 커넥션 10개가 꽉 찼고, 연결을 기다리는 요청이 249개까지 쌓였다. 여러 API가 함께 느릴 때는 모두가 쓰는 자원부터 의심한다.

그런데 DB 세션 상태를 1초마다 찍어 보니, DB는 커넥션을 쥔 시간의 **72%**를 그냥 기다리고 있었다. 가장 오래 쥔 것은 좌석 상태 조회였다.
응답에는 세 열이면 되는데 좌석 15,000개를 열 11개짜리 엔티티로 읽어(약 1.8MB) 받고 변환하는 동안 커넥션을 쥐고 있었다. 같은 쿼리가 DB 안에서는 8.8ms, 서버에서는 36~42ms였다.

필요한 세 열만 읽도록 바꿨다.

```java
@Query("""
        select new ...PerformanceSeatStateRow(s.id, s.seatId, s.state)
        from PerformanceSeat s
        where s.performanceId = :performanceId
        order by s.seatId
        """)
```

| 초당 40명 | 전 | 후 |
| --- | --- | --- |
| 사용자 p99 | 11,084ms | **174ms** |
| 사용자 한 명이 커넥션을 쥔 시간 | 285ms | 43ms |

이제 초당 80명까지 통과했다.

배운 점: 응답에 필요 없는 열을 읽으면, 받고 변환하는 내내 커넥션을 쥔다.

## 3. 커넥션을 두 배로 늘렸는데 그대로였다

초당 100명에서 다시 막혔다. DB는 여전히 대부분 놀고 있어서 커넥션 풀을 10개에서 20개로 늘려 봤다. 결과는 그대로였고, 오히려 커넥션 한 번을 쥐는 시간이 **8.2ms에서 17.8ms로 두 배**가 됐다.

1초에 처리하는 커넥션 사용 횟수는 "커넥션 수 ÷ 한 번 쥐는 시간"이다(Little's law). 풀 10이면 10 ÷ 8.2ms ≈ 1,220번, 풀 20이면 20 ÷ 17.8ms ≈ 1,120번으로 같다.
1초에 1,150대만 통과시키는 톨게이트 앞에서 차선을 늘려도, 줄만 길어지고 통과하는 차는 그대로인 것과 같다.

사용자 한 명이 커넥션을 14번 쓰므로 천장은 1,150 ÷ 14 ≈ 초당 82명이다. 80명은 통과하고 100명은 실패한 결과와 맞는다.
DB도 서버 CPU도 여유가 있었으니, 톨게이트는 둘 사이 어딘가에 있었다.

배운 점: 풀을 늘리기 전에 DB가 실제로 일하는 비율부터 본다.

## 4. 범인은 로컬 Docker 포트 중계였다

서버는 Windows에서, DB는 Docker(Rancher Desktop의 WSL2 가상 머신)에서 돌았다. 그래서 쿼리 하나가 오갈 때마다 Windows와 가상 머신 사이의 포트 중계를 지난다.
서버를 DB와 같은 Docker 네트워크에 띄워 중계를 빼고 같은 부하로 다시 쟀다.

| 초당 100명 | 서버를 Windows에서 | 서버를 DB 옆 컨테이너에서 |
| --- | --- | --- |
| 커넥션 한 번 쥐는 시간 | 8.2ms | **1.7ms** |
| 서버 응답 p95(가장 느린 API) | 1,790ms | **39ms** |
| 커넥션 획득 대기 | 약 200ms | 0ms |

사용자당 커넥션 사용은 그대로 14번이다. 바뀐 것은 서버와 DB 사이 길뿐인데, 커넥션 한 번이 다섯 배 짧아졌다. 운영에서 쓰려는 AWS 구성(서버 → RDS)에는 이런 중계가 없다.

배운 점: 같은 PC에서 하는 로컬 측정은 측정 환경 자체가 병목이 될 수 있다. 의심되면 환경을 바꿔 같은 부하로 비교한다.

## 5. 1MB짜리 응답을 압축했다

서버는 이제 빠르지만 초당 100명은 아직 실패했다. 좌석 상태 응답이 압축 없이 1MB여서, 서버는 28ms에 내보내는데 부하 도구가 다 받는 데 p95 **4.6초**가 걸렸다.
같은 길로 curl은 초당 390~530개를 받으므로, 1MB를 받는 쪽이 밀린다고 봤다.

서버의 응답 압축을 켜고(`server.compression.enabled: true`), 부하 도구도 브라우저처럼 `Accept-Encoding: gzip`을 보내게 했다. 응답이 1MB에서 78KB가 됐다.

| 초당 100명, 부하 도구가 잰 좌석 상태 | 압축 전 | 압축 후 |
| --- | --- | --- |
| p95 | 4,576ms | **24ms** |
| 응답 크기 | 1,050KB | 78KB |

압축 후 값은 6절의 부하 도구 수정까지 마친 뒤 잰 것이다.

배운 점: 서버가 빨라도 응답이 크면 받는 쪽에서 느려진다. 압축은 실제 사용자의 휴대폰에도 그대로 이득이다.

## 6. 마지막 병목은 부하 도구 안에 있었다

압축 뒤에는 서버도 빨랐는데 측정이 자꾸 무효가 됐다. 초당 80명을 고르게 넣어야 하는데, 부하 도구가 1~2초 멈췄다가 몰아서 넣었다(초당 30명 → 138명).
처음에는 PC 메모리를 의심했다. IDE를 끄자 PC 전체가 몇 초씩 멈추던 일은 사라졌지만 짧은 멈춤은 남았다. 그 순간 PC의 CPU와 메모리는 멀쩡했다.

원인은 부하 도구 코드였다. 가상 사용자 한 명이 끝날 때마다 결과 파일을 전역 잠금 아래에서 열고, 한 줄 쓰고, 닫았다.
초당 80번 여닫다가 한 번만 느려져도 잠금을 기다리는 작업 스레드가 모두 멈추고, 그 스레드가 맡은 사용자 투입도 밀렸다. 파일을 한 번 열어 둔 채 한 줄씩 쓰게 바꿨다.

| 초당 80명 | 고치기 전 | 고친 뒤 |
| --- | --- | --- |
| 실제로 들어간 사용자(초당) | 30~138명(무효) | 79~81명 |
| 사용자 p99 | 893ms | **216ms** |

고친 뒤 초당 80명과 100명을 각각 두 번씩 재서 모두 통과했다. 초당 100명에서 사용자 p99는 200~277ms였다.

배운 점: 측정 도구도 측정 대상처럼 의심한다. 투입이 고른지 먼저 확인하지 않았다면 부하 도구의 멈춤을 서버 탓으로 읽었을 것이다.

## 정리

- 여러 API가 함께 느리면 공용 자원부터, 한 API만 느리면 그 쿼리부터 본다.
- 서버가 잰 시간과 클라이언트가 잰 시간, 커넥션을 쥔 시간과 DB가 일한 시간을 나란히 놓으면 시간이 새는 곳이 보인다.
- 효과가 없던 실험(풀 20)이 가장 큰 단서였다.

같은 PC에서 잰 숫자는 병목을 찾는 데까지 쓴다. 실제 수용량은 부하 도구를 다른 서버로 분리한 운영 환경에서 다시 잴 생각이다.
